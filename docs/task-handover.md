# Передача задач проекта

`task:handover` передаёт все доступные незавершённые задачи одного исполнителя в выбранном проекте другому активному участнику этого проекта. Без `--from` источником является текущий пользователь выбранного подключения. Для передачи между двумя сотрудниками руководитель задаёт `--from`.

Сначала проверьте план:

```bash
b24cli task:handover --group-id 234 --responsible 16 --dry-run
b24cli task:handover --group-id 234 --from 14 --responsible 16 --dry-run --json
```

Для выполнения передайте те же параметры без `--dry-run`:

```bash
b24cli task:handover --group-id 234 --from 14 --responsible 16 --json
```

| Параметр | Назначение |
| --- | --- |
| `--group-id ID` | Обязательный положительный ID проекта. |
| `--responsible ID` | Обязательный ID нового ответственного. |
| `--from ID` | Исходный исполнитель; по умолчанию текущий пользователь подключения. |
| `--max-scan N` | Бюджет просмотра доступных задач; по умолчанию 10000. |
| `--dry-run` | Проверить участников и полный список, показать ID и план без записи. |

Источник и получатель должны отличаться и состоять в проекте. `--from` выбирает исполнителя, а права остаются у текущего подключения. Передача не повышает права руководителя автоматически. Нужны разрешение задач (`task` или `tasks`) и `sonet` для [проверки участников](https://apidocs.bitrix24.ru/api-reference/sonet-group/members/sonet-group-user-get.html). `strict-rest3` отклоняет команду до API, поскольку проверка состава проекта использует REST 1.0.

В набор входят `pending`, `in_progress`, `supposedly_completed`, `deferred`, включая задачи без дедлайна. `completed` и `declined` исключены. Список собирается полностью до первой записи, без лимита первых 50 задач. При точном заполнении бюджета допускается одно проверочное чтение следующей страницы: пустая страница подтверждает завершение, наличие ещё одной задачи сохраняет неполный результат без записи. При неполном обходе команда ничего не меняет и возвращает exit 3; увеличьте `--max-scan` или проверьте данные и доступ.

Команда меняет только ответственного. Сроки, статусы, описание и другие роли остаются прежними; сообщения не отправляются. При возвращении из отпуска автоматической передачи назад нет. Новые задачи, появившиеся после снимка списка, требуют отдельного запуска. Область проверки — доступные подключению задачи; CLI не доказывает наличие или отсутствие недоступных ему задач.

Перед каждым назначением проверяются членство участников, проект, прежний исполнитель и открытое состояние задачи. После записи проверяется новый исполнитель. Если обнаружен конфликт или ошибка, следующие назначения прекращаются. Ранее выполненные назначения сохраняются.

JSON возвращает `data.items` с `taskId`, `title`, `fromUserId`, `responsibleId`, `status`, `reason`. В `meta` видны `selected`, `confirmed`, `selectionComplete`, `complete`, `outcomeUnknown` и параметры передачи. `responsibleId` в строке — выбранный получатель; только `status=confirmed` подтверждает его фактическое назначение. Plain выводит те же шесть полей TSV без заголовка, сводку — в stderr.

| Статус строки | Значение |
| --- | --- |
| `confirmed` | Новый ответственный и проект подтверждены повторным чтением. |
| `failed` | Проверка или изменение отклонено. Причина указана в строке. |
| `unverified` | API подтвердил изменение, но последующее чтение не подтвердило итог. |
| `unknown` | Ответ изменяющего запроса потерян; фактический результат неизвестен. |
| `skipped` | Назначение не выполнялось, в том числе после остановки. |

Полный результат возвращает exit 0; частичный — 3; прерывание — 130. Отказы на подготовке сохраняют стандартную диагностику. При `unknown` или `unverified` сначала проверьте `b24cli task:show TASK_ID --json`, затем решайте, нужен ли повтор. Изменяющие запросы автоматически не повторяются, весь набор не является одной транзакцией.

Команда покрывает передачу работы в [EMP-09 и PM-04](task-jtbd.md). Наличие реализации и тестового класса не подтверждает сквозную приёмку на вашем портале. Dedicated integration case требует `B24CLI_TEST_HANDOVER_GROUP_ID` для изолированного проекта и второго test webhook; перед созданием fixtures проверяется отсутствие другой открытой работы источника. Без этих условий тест пропускается.
