# Передача задач проекта

`task:handover` передаёт выбранные незавершённые задачи одного исполнителя другому активному участнику проекта. Без `--from` источник — текущий пользователь подключения. Руководитель указывает исходного сотрудника через `--from`; команда работает с правами текущего подключения.

Пример запроса: «Перенеси отложенные задачи Юлии на меня, кроме 92888, на меня тоже в отложенные». Сначала определите ID сотрудников и проекта и проверьте выборку:

```bash
b24cli task:handover --group-id 234 --from 14 --responsible 16 \
  --source-status deferred --exclude-id 92888 --target-status deferred --dry-run --json
```

Для исполнения уберите `--dry-run`. ID — образцы; команда не выбирает сотрудника по имени.

| Параметр | Назначение |
| --- | --- |
| `--group-id ID` | Обязательный ID проекта. |
| `--responsible ID` | Обязательный ID получателя. |
| `--from ID` | Исходный исполнитель; по умолчанию пользователь подключения. |
| `--source-status STATUS` | Только `pending`, `in_progress`, `supposedly_completed` либо `deferred`. Без опции выбираются все четыре состояния. |
| `--exclude-id ID` | Исключение по ID, можно повторять; одинаковые ID дедуплицируются. |
| `--target-status STATUS` | `pending`, `in_progress`, `deferred`, `supposedly_completed` либо `completed`. Без опции сохранить исходный статус каждой задачи. |
| `--max-scan N` | Бюджет обхода, по умолчанию 10000. |
| `--dry-run` | Полностью собрать выборку, показать ID, исключения и условный план без записей. |

Источник и получатель должны отличаться и состоять в проекте. Требуются разрешение задач (`task` либо `tasks`) и `sonet` для [проверки участников](https://apidocs.bitrix24.ru/api-reference/sonet-group/members/sonet-group-user-get.html). `strict-rest3` запрещает команду до credentials/API: состав и lifecycle используют REST1. Основные чтения и назначение используют REST3.

Выборка включает доступные подключению задачи проекта, в том числе без дедлайна. Исходные `completed` и `declined` исключены; указать их как `--source-status` нельзя. До первой записи собираются все страницы и применяются исключения. Неполный обход даёт exit 3 без записей. При точном заполнении бюджета одно чтение пустой следующей страницы подтверждает завершение; дополнительная задача или ошибка сохраняют неполный результат.

Перед назначением проверяются активное членство, проект, прежний исполнитель и точный исходный статус снимка. Изменение одного открытого статуса на другой также считается конфликтом. Назначение меняет только `responsibleId`; затем проверяются новый исполнитель, проект и сохранение исходного статуса. Сроки, описание и другие роли команда не меняет; сообщения и автоматическая передача назад отсутствуют.

При явной цели выполняются штатные переходы с проверкой фактического состояния:

| Цель | Возможные действия |
| --- | --- |
| `deferred` | `defer`; из ожидания контроля сначала `disapprove`; если уже deferred, переход не нужен. |
| `in_progress` | `start`; из ожидания контроля сначала `disapprove`. |
| `pending` | `pause`; из deferred — `start` → `pause`; из ожидания контроля — `disapprove` и при необходимости `pause`. |
| `supposedly_completed` | `complete` при `needsControl=true`; если сервер завершил задачу, цель не достигнута. |
| `completed` | `complete`; если получено ожидание контроля — `approve`. Из ожидания контроля сразу `approve`. |

Каждое действие требует актуального разрешения подключения. Завершение использует существующую проверку обязательного native result; CLI не создаёт результат. Неизвестные настройки контроля блокируют действие. Одна mutation не повторяется; план ограничен тремя различными действиями. `declined` не поддержан как цель: документированного штатного действия для неё нет.

Права после назначения могут измениться. Если назначение удалось, а переход запрещён, подтверждённое назначение сохраняется, пакет останавливается с частичным результатом. Команда не обещает атомарность или откат. `complete` может повлиять на подзадачи при `autocompleteSubTasks`; CLI не меняет эту настройку и не подтверждает состояние всех побочных объектов. Dry-run обозначает условные действия и непроверенные будущие права, а не обещает их успешное выполнение.

После всех действий повторное чтение проверяет ответственного, проект и ожидаемый статус. Проверка относится к моменту чтения; API не предоставляет здесь compare-and-swap. Задачи, появившиеся после снимка, требуют отдельного запуска.

JSON возвращает `data.items` и `meta`. В строке доступны `taskId`, `title`, `fromUserId`, `responsibleId`, `sourceStatus`, `targetStatus`, `actualStatus`, `assignmentStatus`, `transitionStatus`, `verificationStatus`, `transitionActions`, общий `status` и `reason`. `targetStatus` — ожидаемый статус; без опции равен исходному. `actualStatus=null` означает отсутствие подтверждённого состояния после записи. `transitionActions` хранит известные результаты отдельных действий. `meta.assigned` считает подтверждённые назначения, `meta.confirmed` — полные успешные операции; `selected`, `sourceStatus`, `excludedIds`, `targetStatus`, `selectionComplete`, `complete` и `outcomeUnknown` описывают пакет.

| Общий status | Значение |
| --- | --- |
| `confirmed` | Ответственный, проект и ожидаемый статус совпали. |
| `partial` | Назначение подтверждено, но переход не достиг цели. |
| `failed` | Назначение не выполнено из-за отказа или конфликта. |
| `unknown` | Исход отправленной mutation неизвестен; подтверждённые компоненты сохранены. |
| `unverified` | Есть ACK, но итоговая карточка не подтверждена. |
| `skipped` | Запись не выполнялась, в том числе после остановки. |

`assignmentStatus` принимает skipped/failed/unknown/unverified/confirmed. `transitionStatus` дополнительно использует `not_requested` (сохранение исходного статуса) и `not_needed` (цель уже достигнута). `verificationStatus` — skipped/failed/unverified/confirmed. Plain TSV и human показывают колонки `taskId, title, fromUserId, responsibleId, status, reason, sourceStatus, targetStatus, actualStatus, assignmentStatus, transitionStatus, verificationStatus`. Сводка plain идёт в stderr.

Успех — exit 0, частичный результат — 3, отмена — 130. Некорректные параметры отклоняются до API с exit 2. При unknown/unverified сначала проверьте `b24cli task:show TASK_ID --json`; автоматического повтора нет.

Команда покрывает выборочную передачу [EMP-09 и PM-04](task-jtbd.md). [Unit-контракты](../tests/Unit/TaskHandoverSelectionStatusTest.php) проверяют все пять целей, исключения и частичные исходы. [Integration cases](../tests/Integration/Task/HandoverTasksCommandTest.php) требуют явно изолированного `B24CLI_TEST_HANDOVER_GROUP_ID`, второго webhook и пустой открытой выборки источника до создания fixtures. Без этих условий тесты пропускаются. Реальные задачи пользователей не используются; наличие команды и mock-проверки не подтверждают приёмку на портале.
