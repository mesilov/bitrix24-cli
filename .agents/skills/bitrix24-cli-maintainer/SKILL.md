# Мейнтейнер bitrix24-cli

Следуй правилам [AGENTS.md](../../../AGENTS.md) в корне репозитория.

## Разработка через OpenSpec

- Веди требования, решения и задачи в `openspec/`: актуальные спецификации — в `openspec/specs/`, изменения — в `openspec/changes/`.
- Перед реализацией новой функции, исправления или изменения поведения создай либо обнови соответствующий OpenSpec change и необходимые артефакты.
- Используй локальные скиллы: [openspec-propose](../openspec-propose/SKILL.md) для подготовки, [openspec-apply-change](../openspec-apply-change/SKILL.md) для реализации, [openspec-verify-change](../openspec-verify-change/SKILL.md) для проверки и [openspec-archive-change](../openspec-archive-change/SKILL.md) для завершения. Для корректировки существующих артефактов используй [openspec-update-change](../openspec-update-change/SKILL.md).
- Отмечай задачи выполненными по факту реализации и проверок. Архивируй change после завершения реализации и проверки соответствия спецификациям.
- Не используй workflow Superpowers и не создавай его планы в `docs/superpowers/`.
- Сохраняй незакоммиченные изменения пользователя, не относящиеся к текущей задаче.

## Сопровождение документации JTBD

- При добавлении или изменении JTBD, а также при реализации или изменении связанных CLI-команд обновляй [JTBD по ролям](../../../docs/task-jtbd.md) в том же MR. Сверяй документ с актуальными каноническими требованиями `openspec/specs/`, фактическим `src/Bootstrap/CommandCatalog.php` и файлами `tests/Integration/`; несвязанные изменения не требуют правки JTBD.
- Сохраняй существующие ID сценариев; новые ID бери из OpenSpec. Обновляй затронутые роли и навигацию, формулировки сценариев, таблицы «Статус / Команда / Тест», статусы ✅ Готово / 🕓 План, ссылки с именами файлов интеграционных тестов, границы покрытия, число сценариев и дату/source SHA снимка.
- Статус ✅ Готово означает наличие реализации команды; файл теста и успешная проверка команды отдельно не доказывают полное выполнение JTBD или live-приёмку. Явно сохраняй непроверенные части и планируемые команды.
- Перед открытием MR и непосредственно перед merge в `dev` проверяй актуальность затронутых сценариев и рабочих ссылок после синхронизации с `dev`. Не объявляй реализацию JTBD готовой к поставке, пока соответствующий документ не обновлён.

## Документация Битрикс24 через обязательный MCP

- При любой работе с документацией Битрикс24, планировании API-контрактов, реализации и проверке интеграций обязательно используй [официальный MCP документации Битрикс24](https://apidocs.bitrix24.ru/ai-tools/mcp.html). Сначала вызывай `bitrix-search`, затем `bitrix-method-details`, `bitrix-event-details`, `bitrix-article-details` или `bitrix-app-development-doc-details` по точному имени из результата поиска. Проверяй именно используемую версию REST API и сохраняй ссылки на первоисточники и границы проверки в change.
- Обязательное подключение для проекта задано в [.codex/config.toml](../../../.codex/config.toml): сервер `bitrix24_dev`, `https://mcp-dev.bitrix24.tech/mcp`, Streamable HTTP, `enabled = true`, `required = true`. Проверяй загрузку настроек из доверенного checkout и реальный ответ MCP по правилам `AGENTS.md`; наличие записи в config или `codex mcp list` не является доказательством рабочего подключения.
- Если MCP недоступен, восстанови подключение или сообщи препятствие и останови зависимую от документации работу. Не подтверждай имена, типы и обязательность API-полей по памяти. Сервер предоставляет только документацию и не требует авторизации; не передавай ему токены, вебхуки и другие секреты.

## Имена и типы полей Bitrix24 API

- Поля Bitrix24 в JSON, конфигурации (включая default.task), OpenSpec, примерах и API payload должны называться точно как в используемой версии REST API, с тем же регистром. Не вводи собственные синонимы, aliases или переименование при отправке. Например, в REST 3.0 задач автор — creatorId, исполнитель — responsibleId, группа — groupId, учёт времени — allowsTimeTracking; authorId вместо creatorId недопустим. Это правило относится к API-полям; служебные контейнеры конфигурации profiles/default/task имеют собственную структуру.
- Перед постановкой или изменением требования сверяй имя, тип, обязательность и доступность записи с официальной документацией именно используемой версии API; при необходимости — с API schema/метаданными в рамках разрешённых проверок. Сохраняй ссылку и границы проверки в change. Не переноси имена или Y/N из REST 1.0 в REST 3.0 без проверки.
- Контролируй согласованность issue ↔ proposal/design/spec/tasks, JSON-примеров, config schema, CLI mapping и итоговых API fields. При обнаружении расхождения исправь его в рамках разрешённого объёма до начала реализации или до подтверждения готовности. Уточнение planning не является доказательством исправления runtime-кода.
- При реализации включай в критерии приёмки и целевые проверки одинаковые имена и типы config/API fields и отклонение неподдерживаемых альтернативных ключей без молчаливого переименования. При verify и перед MR проверяй этот контракт вместе с issue ↔ change; не объявляй изменение готовым при расхождении.
- CLI может использовать kebab-case и существующие сокращённые флаги, но они должны однозначно соответствовать документированным API-полям. Переименование существующего CLI-флага требует явно согласованного изменения поведения и миграции; не выполняй его попутно.

## Управление разработкой в GitHub

- Управляй разработкой через GitHub issues и milestones.
- Каждый OpenSpec change должен иметь трассировку хотя бы с одним GitHub issue; каждое поставленное issue должно трассироваться в OpenSpec change.
- Каждое issue должно быть привязано к milestone. Проверяй привязку при разборе и перед началом реализации. Если подходящий milestone не определён, уточни его у пользователя; не назначай произвольный milestone.
- Используй стандартную категоризацию GitHub issues: применяй существующие типы issues и стандартные labels репозитория согласно характеру задачи. Перед назначением проверяй доступные категории в GitHub; не вводи собственную схему категоризации.

### Трассировка issues и changes

1. При разборе issue найди соответствующий существующий change. Если подходящего нет, подготовь новый через `openspec-propose`; не начинай реализацию до появления необходимых артефактов.
2. В `proposal.md` change добавь раздел `## GitHub issues` с полным URL и номером каждого связанного issue. Кратко укажи, какие требования issue покрывает этот change.
3. В описании GitHub issue добавь раздел `## OpenSpec` с идентификатором и путём `openspec/changes/<change-id>/`. Если issue покрывают несколько changes, перечисли их и укажи область каждого.
4. Перед реализацией и при завершении проверь обе стороны связи. После архивирования change обнови путь в issue на фактический путь в `openspec/changes/archive/`.

Изменяй GitHub issue в рамках разрешённой пользователем работы с ним. Если изменение issue недоступно или не разрешено, сохрани ссылку на issue локально в change и явно сообщи, что обратная связь в GitHub ещё не добавлена. Не объявляй трассировку полной до проверки обеих сторон.

## Обязательный changelog для работы над issue

- Каждый MR в `dev` в рамках любой работы над issue обязан содержать содержательную правку [CHANGELOG.md](../../../CHANGELOG.md). Это относится к функциям, исправлениям, документации, tooling и последующим MR архивирования OpenSpec по issue.
- Добавляй запись в `Unreleased` по существующему формату changelog: кратко опиши поставляемый результат и укажи ссылку на связанное issue. Запись должна соответствовать итоговому объёму именно этого MR.
- Перед открытием MR и непосредственно перед merge в `dev` проверяй актуальный diff MR, например `git diff <remote>/dev...HEAD -- CHANGELOG.md`: файл должен быть изменён, а diff должен содержать запись о работе над issue. Наличие файла, старой записи в базовой ветке или только форматирования не выполняет это требование. Повторяй проверку на текущем SHA после обновления ветки и разрешения конфликтов.
- Без такой правки changelog не объявляй MR готовым и не выполняй merge, даже при зелёном CI. Добавь или исправь запись и повтори проверку перед merge.

## Ветки и worktree

- `main` — protected branch, где собираются релизы. Не выполняй прямые push в `main` и не обходи защиту ветки.
- `dev` — ветка, где накапливаются предрелизные изменения.
- `builds` — постоянная ветка выбранных снимков `dev` для ручной проверки промежуточных бинарников и RC перед релизом. Она не является веткой разработки или автоматическим зеркалом `dev`; пользуйся двумя режимами ниже.
- Для остальных работ используй ветки `feature/issueID-issue-title` или `bugfix/issueID-issue-title`: `issueID` — номер GitHub issue без `#`, `issue-title` — краткое название issue в kebab-case. Например, `feature/42-add-contact-export` или `bugfix/57-fix-auth-timeout`.
- Каждую feature- и bugfix-задачу выполняй в отдельном Git worktree, созданном от актуальной `dev`.
- Результат задачи отправляй на ревью через GitHub pull request (MR) из ветки задачи обратно в `dev`.

### Ручные промежуточные и RC сборки через builds

Используй `builds` вручную по запросу пользователя в двух случаях:

- **Промежуточная проверка:** нужно проверить работу standalone-бинарника по выбранному промежуточному снимку `dev`. Перенеси этот снимок в `builds` обычным merge или fast-forward; push запустит три native платформы. Версия — `dev-<полный SHA коммита builds>`, artifacts доступны в соответствующем Actions run без GitHub Release. Повтор того же снимка возможен через `gh workflow run package-static.yml --ref builds`.
- **RC перед релизом:** выбран кандидат из `dev`, который нужно прогнать и протестировать, включая бинарники. После выбора и успешной сборки снимка `builds` создай явно согласованный тег `MAJOR.MINOR.PATCH-rc-N`, начиная с `0.2.0-rc-1`, затем `0.2.0-rc-2` и т.д. Тег указывает на точный выбранный builds SHA, а не на плавающий tip `dev`; push RC-тега запускает отдельную сборку с версией, равной тегу. Проверяй именно эти RC artifacts. RC workflow не публикует Release и не меняет latest.

Для обоих режимов:

- До promotion проверь актуальные remote refs, чистоту отдельного checkout и scope выбранного `dev` snapshot. Не запускай promotion по каждому dev push, расписанию или без запроса на сборку. Не вливай `builds` обратно в `dev`/`main`; исправления делай через обычный issue/change/feature или bugfix → `dev`, затем выбирай новый снимок.
- Сохраняй историю `builds`; не используй force push/reset. Использованный RC-тег не перемещай и не перезаписывай: после исправлений выпускай следующий номер. Перед созданием проверь отсутствие тега локально и в remote.
- Перед считыванием результатов проверь terminal status всех platform и archive jobs. В отчёте сохраняй выбранный dev SHA, фактический builds/tag SHA, run URL/ID, version/build metadata, SHA256SUMS и границы native/manual/portal проверок. Архивы, checksums и metadata должны происходить из одного run.
- Проверяй скачанные бинарники вне checkout: версию, `--about`, общий и командный help, установку и согласованные сценарии; native smoke не заменяет ручную/portal приёмку. Диагностика хранится 7 дней, итоговые archives — 30 дней; скачай нужные evidence до истечения срока.
- Создание RC-тега, проверка кандидата, promotion в `main`, stable tag и публикация Release — отдельные действия. Запрос на intermediate/RC проверку не разрешает автоматически выпуск stable. Не переименовывай dev/RC binaries в stable: финальная версия получает свою сборку и приёмку.

Команды обновления `builds`, скачивания по run ID и проверки checksum/metadata: [build/README.md → Промежуточные снимки из dev](../../../build/README.md#промежуточные-снимки-из-dev). Детали RC: [build/README.md → Ручной RC перед релизом](../../../build/README.md#ручной-rc-перед-релизом).

### Порядок работы над feature или bugfix

1. Определи GitHub issue, его категорию и milestone; проверь или подготовь связь с OpenSpec change.
2. Проверь состояние checkout и remotes. Получи актуальную `dev` из соответствующего remote через `git fetch <remote>` и обнови локальную `dev` до `<remote>/dev` только fast-forward. Не используй `reset --hard`, не перезаписывай локальные коммиты и изменения пользователя. Если обновление невозможно из-за расхождения истории или состояния checkout, сообщи препятствие до создания ветки задачи.
3. Создай отдельный worktree с новой веткой по указанной схеме от обновлённой `dev`, например: `git worktree add -b feature/42-add-contact-export <worktree-path> dev`.
4. В worktree задачи создай или обнови необходимые OpenSpec-артефакты, сверь имена и типы Bitrix24 API-полей по правилу выше, реализуй задачи change и выполни проверки.
5. Непосредственно перед открытием каждого MR в `dev` выполни свежий `git fetch <remote>` и в worktree задачи интегрируй `<remote>/dev` в ветку задачи через `git merge --no-edit <remote>/dev`. Обновление `dev` при создании worktree не заменяет этот шаг. Если появились конфликты, разреши их с сохранением согласованных изменений обеих веток, заверши merge и повтори затронутые проверки. Проверь отсутствие неразрешённых конфликтов и незавершённого merge; до этого MR не открывай.
6. Перед MR проверь трассировку issue ↔ change, milestone, категорию issue, обязательную содержательную правку `CHANGELOG.md` со ссылкой на issue, соответствие имён/типов полей API во всех артефактах и коде и результаты проверок после синхронизации с remote `dev`. Опубликуй ветку задачи и открой MR с целевой веткой `dev`; в описании укажи связанное issue, OpenSpec change и выполненные проверки. Непосредственно перед merge повторно проверь changelog по правилу выше.
7. После подтверждённого merge в `dev` и закрытия связанного issue обязательно выполни порядок завершения ниже: архивируй OpenSpec change и удали связанный worktree. Эти действия входят в завершение уже разрешённой задачи; не оставляй их на отдельное напоминание пользователя.

### Завершение после merge в dev

1. Проверь актуальное состояние в GitHub: MR действительно merged, его целевая ветка — `dev`, связанное issue закрыто. Включённый auto-merge или успешные проверки сами по себе не подтверждают merge.
2. Архивируй связанный OpenSpec change через [openspec-archive-change](../openspec-archive-change/SKILL.md), проверив завершение задач и соответствие реализации спецификациям. Синхронизируй необходимые delta specs с `openspec/specs/`, затем перенеси change в `openspec/changes/archive/`. Актуальные спецификации остаются в `openspec/specs/`. Если change уже архивирован, проверь архив и синхронизацию, не создавай повторный архив. Обнови путь в разделе `## OpenSpec` закрытого issue и проверь обратную ссылку из архивного `proposal.md`.
3. До удаления worktree сохрани результат архивирования и синхронизации в Git и доставь его в `dev` через MR в рамках разрешённой работы. Если архивирование выполнено после исходного merge, используй отдельный MR в `dev`; проверь его merge. Архив не должен остаться только в удаляемом worktree.
4. Проверь связанный worktree: незакоммиченные и untracked-файлы, нужные ignored-файлы и локальные коммиты, которые ещё не сохранены вне него. Сначала сохрани нужные данные; если это невозможно в рамках разрешённой работы, оставь worktree и явно сообщи препятствие. Останови запущенное окружение этой задачи перед удалением checkout. До удаления перейди в основной или другой сохраняемый checkout и выполняй последующие проверки оттуда: удаление текущего каталога ломает дальнейшие команды. Для обычного worktree используй `git -C <surviving-checkout> worktree remove <worktree-path>` без `--force`. Для управляемого Codex worktree используй `archive_worktree` с идентификатором из `list_artifacts`, чтобы сохранить восстанавливаемый снимок и удалить checkout. Не удаляй основной checkout или worktree другой задачи.
5. Из сохраняемого checkout проверь результат через `git -C <surviving-checkout> worktree list` и, для управляемого worktree, `list_artifacts`. В итоговом отчёте укажи фактический путь архива и результат удаления связанного worktree. Если архивирование, обновление трассировки или удаление worktree не завершено, явно перечисли оставшиеся действия.
