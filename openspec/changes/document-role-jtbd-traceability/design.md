# Design

## Context

См. proposal.md. Источники: канонический task-workflows (19 IDs), jtbd-coverage (связи), текущий CommandCatalog (30 task commands), tests/Integration/Task (command:* и happy-path).

## Goals / Non-Goals

Сделать существующий контракт доступным из docs и README. Сохранить исходные роли и IDs в OpenSpec, явно показать соответствие пользовательской группировки. Не расширять runtime, API scope, права доступа и не создавать новые acceptance tests.

## Decisions

- Один раздел на роль, 6/6/7 сценариев с отдельными заголовками и списками. ID связывает сценарий с каноническим Scenario; названия и WHEN/THEN/цель/успех берутся оттуда. Замена IDs потребовала бы миграции всей трассировки, поэтому не выполняется.
- Текущие команды = remaining_commands исходной матрицы, пересечённые с текущим CommandCatalog. Остальные mapped commands явно планируемые. Не считать старый planning catalog доказательством runtime.
- В каждом сценарии блок текущих команд — таблица «Статус / Команда / Тест» со ссылками на реализации и существующие command test Class::method. Статус «Реализована» означает наличие команды в текущем коде, а не успешный запуск теста. Для пустого mapping отдельная строка «Нет реализации / — / Нет». Дополнительные тесты/ручные обходы не добавляются в исходный mapping.
- Поле «Границы» объясняет пределы командных tests и недостающие бизнес-проверки. Отдельного end-to-end теста на каждый JTBD нет; отсутствие ссылок для четырёх пустых mappings показывается явно.
- Проверка — точное множество IDs/текстов, равенство mapping, существование всех локальных ссылок, классов и методов, git diff --check и OpenSpec strict. Для документации достаточно статической проверки; live suite не запускается.

## Risks / Trade-offs

- Снимок может устареть при новых командах → указывать source SHA/дату и инструкцию обновлять список вместе с командами/tests.
- Роль «руководитель отдела» шире исходной проектной роли → список сохраняет именно существующие проектные сценарии PM, не обещает дополнительные отделовые сценарии.
- Наличие tests ошибочно трактуют как acceptance → явные пробелы, ссылка #42 и граница проверки в каждом сценарии.

## Migration Plan

Поставить через MR в dev. После merge/закрытия issue архивировать docs-only change без синхронизации новых specs, обновить обратную ссылку issue и сохранить архив перед удалением worktree.
