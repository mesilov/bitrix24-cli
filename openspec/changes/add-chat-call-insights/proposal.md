# Proposal

## Why

Созвоны команды идут в чатах, но в истории чата от них остаются только служебные строки «Начат звонок №N» и «Звонок завершён (…)». `task:chat:list` и планируемый `chats:messages:list` (#180) отбрасывают `params` сообщения, поэтому агент не может отличить звонок от текста и не получает ни длительности, ни участников. Собирать эти данные из нескольких REST-вызовов и выводить присутствие должен CLI: правила должны давать одинаковый результат при каждом запуске и проверяться тестами, а не придумываться агентом заново.

## What Changes

- Добавить JTBD **CHAT-03 — Итоги созвона**, **CHAT-04 — Кого ввести в курс после планёрки**, **CHAT-05 — Есть ли запись созвона**, **PM-10 — Ритм планёрок за период** и **PM-11 — Кто сейчас на связи** и раздел в `docs/task-jtbd.md` со статусом «план».
- Размечать сообщения о звонке в истории чата (`kind`, `callRef`) вместо потери `params`.
- По умолчанию обогащать звонки из выбранного окна истории данными `im.call.get` и выводом участников по фиксированным версионируемым правилам; флаг `--no-call-details` отключает обогащение.
- Заполнять подтверждённых участников из документированного AI Follow-up звонка (`call.followup.get`, REST 3.0, scope `call`), если он есть; иначе указывать причину.
- Добавить read-only команды `chats:calls:list` (звонки чата за период, PM-10), `chats:calls:show` (один звонок, CHAT-03/CHAT-05) и `users:presence` (последняя активность участников, PM-11).
- Никогда не выводить и не логировать секреты подключения к звонку из ответа `im.call.get` (`connectionData.jwt`, `publicChannels`, `logToken`).
- Объявить новые маршруты REST 1.0 (`im.call.get`, `im.user.list.get`) и необязательный REST 3.0 `call.followup.get` в route policy и scope manifest; `strict-rest3` отклоняет команды до подключения.

## Capabilities

### New Capabilities

- `chat-calls`: разметка звонков в истории чата, обогащение данными звонка, правила вывода участников, состояние записи и ИИ, звонки чата за период и защита секретов подключения.

### Modified Capabilities

- `task-workflows`: добавить PM-10 и PM-11 с измеримыми признаками успеха.
- `user-directory`: добавить чтение последней активности и отсутствия участников (`users:presence`) без опоры на признаки онлайна.

## Impact

Зависит от #180: `chats:messages:list`, разбор TARGET, период и `Rest1ImDialogAdapter` пока находятся в ветке `feature/180-unified-chat-access` и не влиты в `dev`. Часть, не зависящая от #180 (`task:chat:list`, `users:presence --user-id`), реализована сразу по решению пользователя; задачи `chats:*` и TARGET начинаются после merge #180. Изменение затрагивает адаптер истории чата (сохранение `params`), новый порт и адаптер звонков, сервис вывода участников, адаптер `im.user.list.get`, presenter, `CommandCatalog`, API policy и scope manifest, тесты и документацию (`docs/chats.md`, CLI map, scope docs, каталог JTBD).

`im.call.get` не описан в документации Битрикс24 (проверено официальным MCP 12.11.2026) и отсутствует в ответе `methods`, хотя работает через webhook со scope `im`. Это главный риск контракта: портал может изменить или закрыть метод. Дизайн требует, чтобы его отказ не ломал чтение истории. Документированный `call.followup.get` даёт фактических участников, но только для звонков с AI Follow-up; на портале проверки метода нет.
