От имени отправителя 16 те же первые два сообщения дали ноль во всех трёх API. Состояние относится к пользователю подключения, а не к responsibleId задачи. Уже создание задачи породило учитываемое системное сообщение: положительное значение не гарантирует человеческое сообщение.

`im.dialog.messages.get` вернул `unread=true` у чужих непрочитанных сообщений, а после прочтения — `false` у старых сообщений, включая собственное. Получение истории счётчики не сбросило; это подтверждается отдельным сравнением после запроса. Чтение в браузере без ответа сбросило их. Поле сообщения нельзя заменять эвристикой «нет ответа».

### Что не установлено

- Буквальный «@» на этой версии интерфейса не воспроизведён: наблюдался числовой бейдж активности.
- При mute UI, вероятно, приоритизирует упоминания. Это вывод из двух опытов, а не подтверждённый общий алгоритм. Ни один из трёх источников не совпал с UI во всех случаях.
- В JSONL `fixtureCounters.TASKS_TASK_UNREAD=true` — результат helper-проверки членства, **не raw-значение API**. Непустая wire-форма раздела не сохранена; parser fixture нужно снять отдельно. Сочетание ручной метки с положительным счётчиком также требует отдельной проверки.
- Ограниченная роль, иной портал/регион/версия, большой объём задач и гонки во время пагинации не проверялись. Автоматические smoke/adapter tests ещё не созданы.

## Небольшой замер времени

По пять последовательных HTTP-запросов каждого метода, одна неизменная задача, wall time клиента включает транспорт и установление соединения:

| Метод | Медиана, мс | Min–max, мс |
|---|---:|---:|
| im.counters.get | 235.05 | 213.96–251.78 |
| im.dialog.get | 260.75 | 247.85–274.75 |
| tasks.task.list + COUNTERS + ID filter | 252.96 | 239.50–269.42 |

Эти пять запросов не доказывают масштабируемую разницу скорости. Выбор `im.counters.get` основан прежде всего на одном снимке всех счётчиков вместо запроса на каждый чат. Стоимость существующего task scan остаётся.

## Следствия для проекта

- Предикат `task:list --unread` — положительный серверный счётчик, включая mute; `TASKS_TASK` и `CHAT_MUTED` соединяются с подтверждённым task chatId.
- `TASKS_TASK_UNREAD` остаётся отдельной ручной меткой и сама не включает задачу. Нельзя складывать её с числом сообщений.
- Источник `unread` сообщения — исходный boolean `im.dialog.messages.get`, неизвестность представляется явно.
- Не обещать точное совпадение с UI, поиск только упоминаний или только человеческих сообщений. Неизвестную схему нельзя считать нулём.
- Выбранное соединение со стороны задач уточняет рекомендацию экспериментального отчёта: `im.dialog.get` больше не требуется для каждой связи; task API уже даёт проверяемый chatId/association.

## Повторная проверка при реализации (13.11.2026)

**Docs MCP.** Подключение `bitrix24_dev` (`https://mcp-dev.bitrix24.tech/mcp`, Streamable HTTP) в этой сессии не было загружено как инструмент; тот же endpoint вызван напрямую по протоколу MCP (`initialize` → `tools/list` → `tools/call`), сервер `b24-dev-mcp` 0.2.0. Поиск `bitrix-search`, затем детали по точным именам:

- `bitrix-method-details im.counters.get` — scope `im`; описаны `TYPE`, `CHAT`, `CHAT_MUTED` (object, chat ID → число), `CHAT_UNREAD` (array; в TS-примере `number[]`), `LINES`, `DIALOG`, `DIALOG_UNREAD`. `TASKS_TASK` и `TASKS_TASK_UNREAD` по-прежнему не описаны.
- `bitrix-method-details im.dialog.messages.get` — у сообщения `unread: boolean` (схема и пример ответа).
- `bitrix-article-details` «Поля задачи в REST 3.0» — `chatId` integer, `chat` object (для select `tasks.task.get`); «Поля задачи» (REST1, `tasks/fields.html`) — `chatId` integer.

**Второй портал, только чтение.** На рабочем портале выбранного подключения (не playground) выполнены `im.counters.get` и по одной странице `tasks.task.list` REST1 (`select: [ID, CHAT_ID]`) и REST3 (`select: [id, chatId]`). Сохранены только типы, без ID и значений:

| Раздел/поле | Наблюдаемая форма |
|---|---|
| `TASKS_TASK` | object, ключи — строки chat ID, значения — integer (203 записи) |
| `CHAT_MUTED` | object, string → integer (408 записей) |
| `TASKS_TASK_UNREAD`, `CHAT_UNREAD` | пустой array |
| `CHAT`, `DIALOG` | object, string → integer |
| прочие (`COLLAB*`, `COPILOT*`, `LINES`, `CHANNEL_COMMENT`, `TYPE`) | не используются |
| REST1 `chatId` | числовая строка |
| REST3 `chatId` | integer |

Подтверждено на втором портале: `TASKS_TASK` существует в той же форме, `TASKS_TASK_UNREAD` присутствует (пустым), пустые разделы приходят как `[]`. Не снято: непустая форма `TASKS_TASK_UNREAD` — для этого нужна ручная метка, то есть запись (`im.recent.unread`) на рабочем портале; она не выполнялась. Парсер принимает только список chat ID по аналогии с документированным `CHAT_UNREAD`; другая форма даёт `null`/partial, а не ложное значение.
