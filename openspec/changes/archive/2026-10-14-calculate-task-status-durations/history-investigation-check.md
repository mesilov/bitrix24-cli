# History identity and completeness investigation — 14.10.2026

## Verified result

Earlier NEW/DELETE are present **in the server HTTP response**. SDK 3.7.0 preserves that response; CLI normalization does not inject them. A separate legacy read exposes the **same TASK_ID** on both earlier and current records. Two new fixtures have disjoint history IDs, and writing to fixture A does not change B. The anomaly is therefore at the portal history/identity boundary, not a local scanner mixing tasks.

The operator confirms no database restore/reinitialization or manual task ID counter change. We have no server allocation, migration or history-table audit evidence. Reuse of an ID/retained orphan logs is compatible with the responses, but the exact reason must not be asserted as a database reset or proven allocator defect. Both REST methods may share backend data; their agreement does not independently establish why the server associates the earlier logs with this ID.

Modern history event IDs are 16396 (earlier NEW), 16516 (earlier DELETE) and 23756 (current NEW). Legacy rows explicitly contain TASK_ID=6324 on all five records (old NEW/DELETE, current NEW, STATUS, TITLE). Dates and field/value pairs agree between methods. REST3 `tasks.task.list` selects `id,created,status` with filter `[["id","=",6324]]`; `created` is not requested from get.

Importantly, current NEW is one second **after** the immutable `created` readback. Even selecting the latest NEW can miss a second of the actual lifetime. A future creation-boundary implementation should declare the list route, validate matching ID/created before and after collection, retain excluded pre-creation events as evidence, and keep source-completeness/status gates independent. This investigation does not silently install that heuristic or mutate history.

Before-create probe for a bounded nonexistent ID 5288 and after-delete reads fail in the SDK. This is denial/nonexistence evidence, **not** an empty history proving exhaustion. The candidate is not asserted to be the ID subsequently allocated. Only owned fixtures are deleted.

## Completeness evidence and its limit

Large fixture 6308 contains **64 rows in one HTTP response**: two earlier NEW/DELETE, current NEW, one STATUS and sixty TITLE changes. All sixty unique values generated by the test are present. No history event IDs are shared with paired fixture 6310; B receives no A STATUS change.

| Request variation | Rows | next / total | Observed result |
| --- | ---: | --- | --- |
| no start, start=0, 50, 10000, -1 | 64 each | absent | identical ID set |
| filter.FIELD=STATUS | 1 | absent | independently observed 2→3 |
| filter.FIELD=REAL_STATUS | 0 | absent | no canonical field returned |
| filter.FIELD=NEW | 2 | absent | both creation records |
| order.createdDate=DESC | 64 | absent | reversed date ordering |

Raw root keys are `result,time`; result keys are `list`. SDK pagination likewise has null next/total. Thus a generic assumption of a fifty-row history page is disproved on this portal, and start cannot be used as an exhaustion probe. Seeing >50 rows and recovering every change we personally generated proves completeness of this bounded fixture, **not** a contract of absence of any server cap, access filtering, retention or hidden old status cycles for arbitrary tasks.

The committed live test `testRawHistoryIsolationAndMoreThanFiftyKnownChanges` repeats HTTP→DTO equality, adapter ID equality, paired task isolation, sixty known changes, start/filter/order probes and read-only CLI output. Run on fixtures 6328/6330: **1 test, 22 assertions, pass**, 63 rows (no STATUS mutation in this variant), all sixty changes present, null navigation, successful owned cleanup. The test is not marked happy-path and never upgrades `sourceCompletenessProven`.

## Official contract research

Required official MCP search then method-details answered for `tasks.task.history.list`, `tasks.task.list` and `task.logitem.list`. Public primary sources were also checked:

- [Modern history method](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-history-list.html): parameters document taskId, filter.FIELD and order; response example contains result.list/time, no next/total. Generic generated client examples discuss fifty rows/start while the parameter table does not define start. That discrepancy cannot serve as an exhaustive-source guarantee.
- [Official documentation source](https://github.com/bitrix-tools/b24-rest-docs/blob/main/api-reference/tasks/tasks-task-history-list.md): same discrepancy; no explicit count or exhaustive-history guarantee found.
- [Legacy log method](https://apidocs.bitrix24.ru/api-reference/tasks/deprecated/task-item/task-log-item-list.html): PHP/JS examples use positional task ID; rows expose TASK_ID and CREATED_DATE. This portal also returns no next/total.
- [CTaskLog::GetList](https://dev.1c-bitrix.ru/api_help/tasks/classes/ctasklog/getlist.php): documents a TASK_ID filter and CDBResult fetch iteration. It does not prove the modern REST controller calls it without limits, so it is not used to override completeness.

## Separate SDK diagnostic obstruction

Unmodified `task.logitem.list` fails with `tasks_error_exception_#256`, expected integer param #0, despite positional `[6324]`. SDK EndpointUrlFormatter appends `bx24_request_id` to REST1 request URLs, except a strict-method allowlist which omits task.logitem.list. The formatter itself documents legacy argument-order sensitivity. A diagnostic-only HTTP client decorator removed that query key **only for task.logitem.list**, kept the request body/header, and the positional call then succeeded. No vendor files or production fallback were changed. This explains the failed legacy diagnostic; it does **not** explain modern history's old NEW/DELETE, already visible before DTO parsing.
