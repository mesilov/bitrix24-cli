# Spec Delta

## Purpose

Дать пользователю и агенту чтение и запись статей Базы знаний 2.0 Битрикс24 через CLI: найти базу и статью, прочитать Markdown, создать статью и заменить её содержимое с явным исходом записи.

## ADDED Requirements

### Requirement: Knowledge base namespace
CLI SHALL предоставлять namespace `kb:*` с командами `kb:list`, `kb:article:list`, `kb:article:search`, `kb:article:show`, `kb:article:add`, `kb:article:update`. Команды SHALL работать только с Базой знаний 2.0 через REST 3.0; старая база знаний на лендингах SHALL не поддерживаться. Справка и `list kb` SHALL работать офлайн.

#### Scenario: Офлайн-справка
- **WHEN** без credentials вызывают `list kb`, completion либо help любой команды `kb:*`
- **THEN** доступны шесть полных имён и их справка без API, чтения secrets или записи конфигурации

#### Scenario: Только База знаний 2.0
- **WHEN** пользователь ищет базу знаний, созданную в старом разделе на лендингах
- **THEN** CLI её не показывает и не обращается к `landing.*`
- **AND** документация называет эту границу явно

### Requirement: KB-01 — Какие базы знаний мне доступны
CLI SHALL возвращать все базы знаний, доступные пользователю подключения, с их ID, названием и уровнями доступа, обходя страницы до конца выдачи. Результат SHALL всегда быть списком, в том числе пустым.

#### Scenario: Выбор базы знаний
- **WHEN** пользователь вызывает `kb:list --json`
- **THEN** `data.items` содержит каждую доступную базу с `id`, `name`, `policyLevel`, `accessLevel` и признаком архива под именами REST 3.0
- **AND** `meta.complete` равен true, когда курсор следующей страницы пуст

#### Scenario: Пагинация не продвигается
- **WHEN** API повторно возвращает уже полученный курсор либо уже полученные ID
- **THEN** CLI останавливает обход, сохраняет полученные базы и возвращает `complete=false`, `reason: pagination-no-progress` и exit 3

### Requirement: KB-02 — Найти статью
CLI SHALL позволять найти статью без знания её ID двумя способами: по структуре одной базы знаний и полнотекстовым поиском по заголовку и содержимому во всех доступных базах. Оба способа SHALL возвращать ID статьи, пригодный для чтения и обновления.

#### Scenario: Структура базы
- **WHEN** пользователь вызывает `kb:article:list --collection 42`
- **THEN** CLI возвращает дерево статей базы с `id`, `parentId`, `title`, `position` и вложенными страницами; архивные статьи в дерево не входят
- **AND** human/plain выводы показывают вложенность и ID каждой статьи

#### Scenario: Обрезанное дерево
- **WHEN** API вернул дерево с признаком `truncated`
- **THEN** CLI возвращает полученные узлы, `complete=false`, `reason: tree-truncated` и exit 3
- **AND** подсказывает искать статью через `kb:article:search`

#### Scenario: Поиск по теме
- **WHEN** пользователь вызывает `kb:article:search --query "отпуск"`
- **THEN** CLI возвращает найденные статьи с `documentId`, `collectionId`, `title`, `score`, `snippet`, `sharedAccess`
- **AND** при `hasMore` вывод сообщает, что за пределами страницы есть ещё результаты, и предлагает уточнить запрос либо увеличить `--limit`

#### Scenario: Некорректный поисковый запрос
- **WHEN** запрос после обрезки пробелов короче 3 или длиннее 200 символов либо `--limit` вне 1…200
- **THEN** CLI возвращает usage-error/exit 2 до credentials и API

### Requirement: KB-03 — Прочитать статью
CLI SHALL возвращать заголовок, содержимое в Markdown и служебные поля статьи по её ID без изменения текста. Режим только содержимого SHALL выводить Markdown байт в байт, без заголовков, рамок и добавленных символов.

#### Scenario: Чтение статьи агентом
- **WHEN** пользователь вызывает `kb:article:show 77 --json`
- **THEN** `data.article` содержит `id`, `collectionId`, `parentId`, `title`, `markdown`, `createdBy`, `updatedBy`, `createdAt`, `updatedAt` и признаки архива и корзины под именами REST 3.0

#### Scenario: Содержимое для правки в файле
- **WHEN** пользователь вызывает `kb:article:show 77 --markdown > article.md`
- **THEN** файл содержит ровно значение `markdown` из API

#### Scenario: Статья не найдена
- **WHEN** статьи с таким ID нет либо она недоступна
- **THEN** CLI возвращает `article-not-found`, exit 1, а не пустую успешную карточку

### Requirement: KB-04 — Создать статью
CLI SHALL создавать статью в выбранной базе знаний, в том числе дочернюю страницу, с заголовком и необязательным Markdown из файла или stdin. Успех SHALL возвращать ID созданной статьи, пригодный для чтения и обновления.

#### Scenario: Новая статья с содержимым
- **WHEN** пользователь вызывает `kb:article:add --collection 42 --title "Регламент отпусков" --markdown-file vacation.md`
- **THEN** CLI создаёт одну статью с `collectionId`, `title` и `markdown` из файла
- **AND** возвращает созданную статью с её `id`

#### Scenario: Дочерняя страница
- **WHEN** передан `--parent 77`, а статья 77 принадлежит другой базе знаний
- **THEN** CLI возвращает ошибку о несоответствии родителя базе знаний и статью не создаёт

#### Scenario: Некорректный ввод
- **WHEN** заголовок после обрезки пуст или длиннее 255 символов, Markdown больше 1 048 576 байт либо не задан `--collection`
- **THEN** CLI возвращает usage-error/exit 2 до credentials и API

### Requirement: Duplicate title guard before article creation
CLI SHALL до создания проверять дерево выбранной базы знаний и не создавать статью, если у того же родителя уже есть статья с точно таким же заголовком, без явного разрешения дубля. Неполное дерево SHALL блокировать создание так же, как совпадение.

#### Scenario: Повторный запуск агента
- **WHEN** у того же родителя уже есть статья с точно таким же заголовком
- **THEN** CLI не создаёт статью и возвращает `article-exists`, exit 4, с ID существующей статьи
- **AND** создание выполняется только с `--allow-duplicate-title`

#### Scenario: Дерево не доказало отсутствие дубля
- **WHEN** дерево базы знаний вернулось с признаком `truncated`
- **THEN** CLI не создаёт статью и возвращает `search-incomplete`, exit 4

### Requirement: KB-05 — Обновить статью
CLI SHALL заменять заголовок и/или содержимое существующей статьи по её ID. Новое содержимое SHALL заменять Markdown статьи целиком; частичная правка SHALL не заявляться. Документация SHALL описывать сценарий: прочитать содержимое, изменить локально, записать полный текст.

#### Scenario: Правка статьи агентом
- **WHEN** агент получил Markdown через `kb:article:show 77 --markdown`, изменил его локально и вызвал `kb:article:update 77 --markdown-file article.md`
- **THEN** CLI отправляет весь текст файла как `markdown` и возвращает статью после изменения
- **AND** заголовок не меняется, если `--title` не передан

#### Scenario: Нечего обновлять
- **WHEN** не передан ни `--title`, ни `--markdown-file`
- **THEN** CLI возвращает usage-error/exit 2 до credentials и API

#### Scenario: Несохранённые правки в совместном редакторе
- **WHEN** запись Markdown отклонена из-за несохранённых изменений статьи в редакторе
- **THEN** CLI сообщает о конфликте и подсказывает повторить с `--overwrite`, если содержимое действительно нужно перезаписать
- **AND** без `--overwrite` CLI не передаёт `overwrite=true` и не перезаписывает статью сам

### Requirement: Explicit article write outcome
CLI SHALL показывать в dry-run метод, базу знаний, ID статьи, заголовок и размер и хеш содержимого без записи. Запись SHALL выполняться одним вызовом без автоматического повтора; потеря ответа SHALL сообщаться как outcomeUnknown. Результат записи SHALL сверяться со статьёй из ответа API.

#### Scenario: Dry-run
- **WHEN** `kb:article:add` или `kb:article:update` вызваны с `--dry-run`
- **THEN** CLI показывает план записи; при создании выполняет только проверку дубля
- **AND** статья не создаётся и не меняется

#### Scenario: Потеря ответа сервера
- **WHEN** запрос мог создать или изменить статью, но ответ не получен
- **THEN** CLI сообщает outcomeUnknown и подсказывает проверить статью через `kb:article:list` либо `kb:article:show` перед повтором
- **AND** повторная запись автоматически не выполняется

#### Scenario: Ответ не совпал с запросом
- **WHEN** статья в ответе API имеет другие заголовок, базу знаний или родителя, чем запрошено
- **THEN** CLI возвращает ID статьи, список несовпавших полей и exit 3

#### Scenario: Сервер нормализовал Markdown
- **WHEN** заголовок, база и родитель совпали, а `markdown` в ответе отличается от отправленного текста
- **THEN** запись считается подтверждённой, а вывод сообщает признак `markdownNormalized` и возвращает сохранённый текст

### Requirement: Knowledge base policy, scope and output
Команды `kb:*` SHALL объявлять полные маршруты REST 3.0 и требовать scope `note` до исполнения; `strict-rest3` SHALL их разрешать. Имена полей в выводе и в запросах SHALL совпадать с REST 3.0. CLI SHALL сохранять human/plain/JSON контракт.

#### Scenario: Нет scope note
- **WHEN** у вебхука нет scope `note`
- **THEN** команда `kb:*` возвращает `scope-missing`/exit 4, а команды задач и чатов работают как прежде

#### Scenario: Тариф без REST
- **WHEN** портал отклоняет вызов `note.*` из-за тарифа без доступа к REST
- **THEN** CLI возвращает явный отказ в доступе, а не пустой успешный список

#### Scenario: Точные имена полей
- **WHEN** CLI создаёт или обновляет статью
- **THEN** запрос использует `collectionId`, `parentId`, `title`, `markdown`, `overwrite`, а JSON-вывод сохраняет имена полей ответа API без переименования
