# Подпись standalone-бинарников bitrix24-cli

Дата проверки документации и цен: **11.10.2026**. Issue: [#25](https://github.com/mesilov/bitrix24-cli/issues/25), milestone `0.1.0`. Это исследование требований и вариантов, без покупки услуг или изменения сборки.

## 1. Область и вывод

База исследования — `origin/dev`, commit `b53178e`, `README.md`, `build/README.md`, `build/package.py`, release workflow и `openspec/specs/binary-distribution/spec.md`. В проекте: Linux amd64 (static musl, проверка в Debian 12, builder Ubuntu 24.04), macOS arm64 (runner macOS 15), Windows amd64 (Windows Server 2022). Это существующая матрица сборки, а не подтверждение совместимости со всеми версиями этих ОС. Публичный релиз в прочитанном README ещё не объявлен. Рассмотрены CI artifacts и release archives, загрузка через браузер, установщик и пакетный репозиторий. macOS Intel/Rosetta и Windows 10/11 ниже — документированные сценарии, не новые поддерживаемые платформы проекта.

**Платный сертификат не является универсальным условием запуска.** macOS arm64 требует корректной подписи, но допускает бесплатную ad-hoc; доверенное распространение через Gatekeeper требует другой цепочки. В Windows подпись удостоверяет издателя, а SmartScreen дополнительно оценивает репутацию. Linux обычно запускает ELF без платного сертификата; подпись возникает в отдельных каналах установки и политиках. Подробные источники и ограничения — ниже.

## 2. macOS: обязательность, обходы, получение

Apple отдельно требует подпись native arm64-кода и допускает ad-hoc без удостоверенной личности; переведённый Rosetta x86_64-код может быть неподписанным. Это не отменяет Gatekeeper для скачанного файла. Начиная с Catalina стандартная проверка интернет-загрузок использует Developer ID и notarization. Источники: [Apple Silicon](https://support.apple.com/en-euro/guide/security/secebb113be1/web), [правила открытия](https://support.apple.com/en-us/102445).

Для разработки подходят локальная сборка и корректная ad-hoc подпись. Для доверенного скачанного файла Apple описывает повторную попытку открытия и **System Settings → Privacy & Security → Open Anyway → Open**. Это разрешение одного файла; управляемая система может запретить действие. Оно не ремонтирует повреждённую подпись и не является универсальным разрешением при обнаружении malware/отзыве сертификата. Применимость этого UI к первому запуску именно нашего CLI пока не проверена. [Apple Support](https://support.apple.com/en-us/102445).

В [#23](https://github.com/mesilov/bitrix24-cli/issues/23) уже зафиксирована ошибка strict validation конечного Mach-O после объединения PHP micro runtime и PHAR; повторная ad-hoc подпись копии не устранила её. Следовательно, объяснять этот сбой только отсутствием оплаченного Developer ID нельзя. Сначала нужно восстановить целостность итогового файла и проверить сохранность PHAR при подписании. Ни результат из issue, ни runner-local smoke не доказывают успешный первый запуск браузерной загрузки.

Путь публичного релиза: Account Holder получает **Developer ID Application**, подписывает итоговый код с hardened runtime и secure timestamp, отправляет ZIP/PKG/DMG через `notarytool`, проверяет Accepted и launch experience. Для подписанного PKG нужен отдельный **Developer ID Installer**. Notarization — автоматизированная проверка и ticket, отдельная от code signature. [Developer ID](https://developer.apple.com/developer-id/), [подготовка notarization](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution), [выпуск сертификатов](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/).

**Особенность CLI:** `.tar.gz` не является непосредственным форматом отправки в notary service. Можно отправить ZIP с подписанным бинарником, но ticket нельзя staple к ZIP или к standalone binary. Для такого файла Gatekeeper ищет ticket онлайн. Для сценария без сети стоит исследовать stapled PKG/DMG; обещать офлайн-проверку текущего bare CLI в архиве нельзя. [Apple: custom notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).

Стоимость программы — **$99 USD за год**, локальная валюта/налоги зависят от региона. Бюджет следующего года — ещё $99 при неизменном тарифе. Отдельного тарифа за каждый Developer ID или notarization в рассмотренных страницах не указано; резерв на непроверенные дополнительные расходы не считаем нулевым автоматически. Физлицо: Apple Account, 2FA, совершеннолетие, юридическое имя и возможная проверка ID. Организация: юридическое лицо, D-U-N-S, полномочия, рабочая почта/сайт; D-U-N-S обычно бесплатен. Регистрация может быть ограничена санкциями, фактические страна заявителя и возможность оплаты здесь неизвестны. [Enrollment](https://developer.apple.com/help/account/membership/program-enrollment/).

OSS-статус сам по себе не освобождает от оплаты: waiver предусмотрен для подходящих nonprofit/educational/government организаций, исключает физлиц и sole proprietors. [Fee waiver](https://developer.apple.com/help/account/membership/fee-waivers/). При истечении Developer ID уже подписанное ПО без специальных provisioning profiles может оставаться пригодным; для новых подписей/выпуска сертификата нужны действительные credentials. Отзыв — отдельное событие с последствиями для запуска. Членство и срок сертификата нельзя смешивать. [Apple: certificate lifecycle](https://developer.apple.com/help/account/certificates/create-developer-id-certificates/).

Для CI потребуется защищённое хранение private key и notary credentials, ограничение доступа release jobs и проверка конечного артефакта. Это инженерная рекомендация; выбранный keychain/export workflow ещё не внедрён и не испытан.

## 3. Windows: обязательность и способы запуска

Для обычного пользовательского EXE Authenticode не является универсальной платной лицензией на запуск. SmartScreen проверяет издателя и hash файла: новая подписанная сборка может предупреждать, у неподписанных версий репутация строится заново. **EV сейчас не даёт автоматического обхода SmartScreen**; покупать его только ради этого нецелесообразно. Self-signed сертификат по умолчанию даёт те же предупреждения, что отсутствие подписи. Управляемая политика может запретить продолжение. [Microsoft: SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).

При обычном предупреждении доступен **More info → Run anyway**, если это разрешено. В свойствах файла можно выбрать Unblock; PowerShell `Unblock-File -LiteralPath .\b24cli.exe` удаляет `Zone.Identifier` с меткой происхождения. Это изменение метаданных конкретного файла, не создание доверенной подписи; оно не выполняет правила SAC/App Control. [Microsoft: Unblock-File](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.utility/unblock-file?view=powershell-5.1).

В Windows 11 **SAC в режиме On** может блокировать неизвестный исполняемый код, если облачная оценка не считает его безопасным и нет доверенной подписи. Проверка применима и к локальным файлам; локальная сборка не гарантирует обход. По FAQ индивидуального исключения нет. Отключение через Windows Security → App & browser control → Smart App Control settings действует на всю систему; для пользовательской инструкции релиза его не рекомендуем. Возможность повторного включения зависит от актуальности устройства; текущий FAQ уже описывает обновления без обязательной чистой переустановки. [SAC overview](https://learn.microsoft.com/en-us/windows/apps/develop/smart-app-control/overview), [SAC FAQ](https://support.microsoft.com/en-us/windows/smart-app-control-frequently-asked-questions-285ea03d-fa88-4d56-882e-6698afdb7003).

Внутри организации администратор может явно доверять собственной CA/издателю или разрешить hash правилами управления приложениями. Это согласованный rollout политики, требует административного доступа и не превращает self-signed сертификат в публично доверенный. Подпись также не переопределяет корпоративный deny rule. [Microsoft: App Control rules](https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/design/select-types-of-rules-to-create).

**Канал Store:** Microsoft подписывает MSIX; для MSI/EXE-публикации через Store издатель должен заранее подписать установщик и PE-файлы доверенной CA. Поэтому «положить наш EXE в Store и получить подпись бесплатно» неверно; MSIX потребует отдельного исследования упаковки CLI и правил канала. [Microsoft: code signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options).

## 5. Linux: ELF, пакеты и бесплатное доверие

Для обычного ELF из архива в стандартной Linux-системе платный code-signing сертификат не требуется. Это **вывод из модели `execve`**, а не обещание для всех конфигураций: нужны права исполнения, совместимая архитектура, разрешённый filesystem и runtime. `chmod u+x ./b24cli` решает только отсутствие execute permission. [Linux man-pages](https://www.man7.org/linux/man-pages/man2/execve.2.html).

APT аутентифицирует `InRelease`/`Release.gpg` репозитория и цепочку hashes до DEB; сам `apt-secure` не проверяет индивидуальные package signatures. Собственный репозиторий можно подписать своим OpenPGP-ключом и подключить через **Signed-By**, без покупки CA. Разрешение insecure/trusted repository отключает соответствующую проверку доверия и не нужно для нашего публичного канала, поскольку подпись своим ключом бесплатна. [Debian apt-secure](https://manpages.debian.org/trixie/apt/apt-secure.8.en.html).

RPM поддерживает OpenPGP-подпись через `rpmsign --addsign`; DNF различает `gpgcheck`, `repo_gpgcheck` и `localpkg_gpgcheck`. Конкретные defaults и принудительная политика зависят от дистрибутива и `%_pkgverify_level`; отключение одного параметра не гарантирует обход всех проверок. [RPM](https://rpm.org/docs/6.1.x/man/rpmsign.1), [DNF](https://dnf.readthedocs.io/en/latest/conf_ref.html).

Корпоративные IMA appraisal/IPE могут запрещать доступ или исполнение по локальной политике доверия. Тогда ключ/правило согласуется с администратором; произвольный публичный сертификат может не подходить. Secure Boot и обязательная подпись **модулей ядра** — отдельные механизмы, их нельзя переносить на обычный b24cli. [IMA maintainers](https://github.com/linux-integrity/ima-doc/blob/main/ima-concepts.rst), [IPE](https://docs.kernel.org/security/ipe.html), [kernel module signing](https://docs.kernel.org/admin-guide/module-signing.html).

Стоимость собственного OpenPGP-ключа и программной подписи GnuPG — **$0 за лицензию**, без годовой оплаты CA. Для публичных архивов возможна detached signature, для APT/RPM — подпись соответствующего объекта. Практические расходы: хранение/backup ключей, ротация, отзыв, публикация нового fingerprint и поддержка доверия пользователей; труд/сервер/HSM не оценены. Hardware key необязателен для обычной software OpenPGP-подписи. [GnuPG](https://www.gnupg.org/).

Альтернатива — бесплатный public Sigstore, `cosign sign-blob` и bundle с подписью, удостоверением OIDC-identity и доказательством transparency log. Получатель должен проверять разрешённые identity/issuer; выбор политики — задача внедрения. Это проверка скачанного объекта, она не заменяет Developer ID/Authenticode и не создаёт автоматического доверия OS. [Sigstore overview](https://docs.sigstore.dev/about/overview/), [signing blobs](https://docs.sigstore.dev/cosign/signing/signing_with_blobs/). Обычный SHA-256 checksum выявляет изменение байтов при доверенном эталоне, но сам по себе не удостоверяет издателя; рекомендация — подписывать manifest или публиковать проверяемый Sigstore bundle.
