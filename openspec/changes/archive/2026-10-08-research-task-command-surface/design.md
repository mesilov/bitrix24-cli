# Design

## Context

См. [proposal.md — Why](proposal.md#why). Базовая dev 5d236a0 содержит Symfony Console без прикладных команд; composer.lock фиксирует b24phpsdk 3.7.0. PHP SDK использует смесь REST 1.0 и 3.0. Основной checkout имеет посторонние незакоммиченные изменения; работа ведётся отдельно в feature/10-research-task-command-surface.

## Goals / Non-Goals

Получить проверяемый каталог операций и проект CLI-интерфейса, который можно обсуждать до реализации. Команды, приоритеты и общий контракт пока кандидаты. Runtime, новый MCP, auth storage, выбор тарифов, миграция зависимостей и сторонний код не добавляются.

## Decisions

1. **Документационный change, skip_specs: true.** Исследование сохраняет текущие факты и явно обозначает предложения. Альтернатива — сразу принять runtime-требования — преждевременна: пользователь запросил исследование и поверхность.
2. **Источники по роли.** Сценарии берём из b24-cli и templates-mcp, REST-имена/версии — из официального b24restdocs, SDK-покрытие — из actual calls закреплённого SDK. Альтернатива «команды upstream = полный API-контракт» скрывает gaps и миграцию карточки.
3. **Раздельные измерения в JSON.** Каждая запись содержит method/path/version, command/syntax, effect, priority, scope, source, sdk и kind. Совпадающие имена REST разных версий остаются разными записями; compatibility и deferred не смешиваются с основными кандидатами.
4. **Symfony namespace tasks:.** Один набор команд для людей и автоматизации; human/JSON меняют вывод. Альтернатива — интерактивное меню как обязательный вход — затрудняет shell/CI. Все названия подлежат ревью.
5. **Современная карточка и явные legacy маршруты.** CRUD/chat/schema предлагаются v3; расширенные фильтры list и lifecycle остаются legacy там, где документация/SDK требуют это. Никакого молчаливого fallback после ошибки. Legacy comments изолированы; создание результата не подменяется комментарием.
6. **Не копировать общую модель данных upstream.** V3 не принимает accomplices/auditors при add/update и требует creatorId. Параметры и JSON-контракт описаны в task-surface.md; версия ответа указывается в meta. Типизированная нормализация между API — работа следующего change.
7. **Проверять матрицу как данные.** JSON и Markdown содержат одинаковые операции; все 98 index entries объяснены, SDK wrapper отличается от legacy batch и Core gap. Скрипты проверки запускаются временно, в приложение не добавляются.

## Risks / Trade-offs

- [Документация и портал могут расходиться] → фиксируем SHA и ограничения; live acceptance нужна в будущем implementation change.
- [Смешение версий/регистра полей] → version и scope в каждой записи, параметры конкретной версии, отдельный renderer вывода.
- [Составная запись может завершиться частично] → явные отдельные операции и вывод результата каждого шага; транзакционность не обещается.
- [Широкий каталог ошибочно воспримут как MVP] → P0/P1/P2 лишь предложение; flows/userfields/events и смежные области deferred.
- [SDK wrapper ошибочно примут за проверенную интеграцию] → wrapper означает статическое наличие метода, не успешный запрос.
- [Метаданные issue types не поддержаны personal repository] → GitHub REST issue не содержит type, PATCH type не сохраняет его, endpoint issue-type возвращает 404; применён доступный стандартный label documentation и milestone 0.1.0.

## Migration Plan

Публикуется только документация в отдельной ветке и PR в dev. Миграция приложения не требуется; отмена документационного commit удаляет артефакты. После ревью поверхности следующий change должен зафиксировать принятый MVP, требования runtime, auth и acceptance на тестовом портале.
