# Design

## Context

См. `proposal.md`, раздел Why. Текущий скилл уже требует отдельного worktree, MR в `dev` и сохранения пользовательских изменений. Проектная конфигурация MCP отсутствует. Официальный MCP Битрикс24 предоставляет документацию по Streamable HTTP без авторизации.

## Goals / Non-Goals

**Goals:** сделать подготовку ветки, завершение задачи и получение документации через официальный MCP обязательными частями workflow, с проверяемым результатом.

**Non-Goals:** автоматическое слияние запрошенного MR, удаление чужих worktree, изменение команд CLI или добавление скриптов автоматизации.

## Decisions

- Добавить свежий `git fetch <remote>` и `git merge <remote>/dev` непосредственно перед публикацией MR. Обновления только при создании worktree недостаточно; merge не требует переписывания истории ветки. При конфликтах завершить их разрешение и повторить затронутые проверки до MR.
- После подтверждённого merge и закрытия issue использовать существующий `openspec-archive-change` и обновлять архивный путь в issue. Уже архивированный change проверять без повторного архивирования.
- Сначала сохранять архив и нужные данные, затем останавливать окружение задачи и удалять только её worktree. До удаления переходить в сохраняемый checkout и выполнять последующие проверки оттуда. Для управляемого checkout использовать `archive_worktree`, для обычного — `git -C <surviving-checkout> worktree remove <worktree-path>` без force.
- Добавить `[mcp_servers.bitrix24_dev]` в `.codex/config.toml`: официальный URL, `enabled = true`, `required = true`. Это проектная конфигурация без изменения пользовательских глобальных настроек. Не добавлять bearer-токены или транспорт `/sse`.
- В `AGENTS.md` и скилле явно требовать `bitrix-search` и соответствующий `bitrix-*-details` для проверки документации. Ссылки на первоисточник сохранять в change; недоступность MCP останавливает только зависимую от документации работу, без подмены проверенных API-контрактов памятью модели.
- Проверять TOML, чтение конфигурации через `codex mcp get bitrix24_dev --json` из checkout и реальный ответ MCP. Пользовательские настройки доверия не менять: документировать, что проектный config загружается только для trusted project.

## Risks / Trade-offs

- Потеря локального архива или данных при удалении checkout → до удаления проверить сохранность результатов в Git и вне worktree; при невозможности сохранения оставить worktree с объяснением.
- Новые изменения `dev` после первоначальной проверки → выполнять fetch и merge непосредственно перед MR и перепроверять затронутые области.
- Недоступность обязательного MCP останавливает запуск/возобновление Codex → явно документировать это требование и восстановление подключения; `required` не гарантирует наличие конкретной страницы в документации.
- Не доверенный checkout пропускает проектный config → указать условие trust в `AGENTS.md`; не выдавать наличие TOML за подтверждение подключения.

## Migration Plan

Опубликовать правки скилла, `AGENTS.md` и проектный config в MR в `dev`. Проектные настройки применяются при новой сессии или возобновлении доверенного checkout. Откат — revert соответствующих коммитов; состояние приложения не меняется.
