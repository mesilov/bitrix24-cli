# Design

## Context

`tasks.task.chat.message.send` (REST 3.0) — документированный преемник `task.comment.add` для чата задачи и возвращает только `true`. ID сообщения можно получить только чтением чата. Похожий readback уже есть в `chats:send`, но там ID известен из `im.message.add`, и чтение лишь подтверждает чат. Здесь ID надо найти.

## Goals / Non-Goals

Цели: вернуть `messageId` и `chatId` после `task:chat:send`; никогда не выдавать чужое или старое сообщение за отправленное; при неоднозначности сообщить об этом, не повторяя запись.

Не цели: смена метода отправки, готовая веб-ссылка, изменение `task:chat:delete`.

## Decisions

### 1. Метод отправки не меняется

Отправка остаётся через `tasks.task.chat.message.send`. Переход на `im.message.add` в `chatN` вернул бы ID сразу, но меняет семантику записи (права участников задачи против прав участника чата, возможное различие в уведомлениях и счётчиках задачи), что выходит за рамки issue. Альтернатива отклонена.

### 2. Чтения до записи

До отправки:

1. `tasks.task.get` с `chat.id/entityId/entityType` — та же проверка привязки, что у `task:chat:update/delete`. Не доказана — `message-binding-unverified`, exit 4, запись не выполняется. В dry-run эта проверка выполняется (как у update/delete).
2. Непосредственно перед записью — `im.dialog.get`: `last_message_id` становится нижней границей поиска (`baseline`). Чтение не меняет состояние прочтения.

Автор — пользователь вебхука из выбранного подключения (`CurrentUserGateway`), без API-вызова.

Следствие: `task:chat:send` теперь требует scope `im`. Остальные `task:chat:*` его уже требуют; пользователю, читающему и пишущему в чат задачи, он и так нужен.

### 3. Readback после записи

`im.dialog.messages.get` с `FIRST_ID = baseline` постранично (по 50) с budget 200 сообщений — тот же сканер, что у `task:chat:list`, с проверкой `chat_id` каждой строки. Кандидат — строка с `authorId` = пользователь подключения и текстом, равным отправленному после нормализации (`\r\n` → `\n`, обрезка пробелов по краям).

| Исход | `readback.status` | Результат |
|---|---|---|
| ровно один кандидат | `verified` | exit 0, `messageId`/`resourceId` заполнены |
| ноль кандидатов | `missing` | exit 3, `messageId = null` |
| несколько кандидатов | `ambiguous` | exit 3, `messageId = null`, `data.readback.candidates` — их ID |
| чтение упало / budget исчерпан без единственного совпадения | `failed` / `incomplete` | exit 3, `messageId = null` |

Во всех исходах после успешной записи `operation.confirmed = true`, `outcomeUnknown = false`, повторной отправки нет. Неуспешный readback: `meta.complete = false`, `meta.reason = readback-unverified` — тот же контракт, что у `chats:send`. Ctrl-C (130) во время readback пробрасывается.

Почему не «последнее сообщение автора»: параллельная запись того же пользователя (другой агент, веб-интерфейс) подменила бы ID. Совпадение автора, текста и окна после `baseline` при единственности кандидата исключает выбор старого сообщения; два одинаковых сообщения одного автора в окне честно дают `ambiguous`.

Риск: сервер может нормализовать текст иначе (BB-коды, упоминания). Тогда исход — `missing`, а не неверный ID. Live-тест проверяет обычный текст и многострочный текст.

### 4. Форма ответа

Профиль остаётся `mutation` (plain-столбцы `taskId, resourceId, action, changedFields` не меняются, `resourceId` теперь заполнен):

```json
{"data": {
  "operation": {"taskId": 123, "resourceId": 9876, "action": "send", "changedFields": ["text"], "confirmed": true,
                "chatId": 456, "dialogId": "chat456", "messageId": 9876, "readback": "verified"},
  "readback": {"status": "verified", "messageId": 9876, "chatId": 456, "baselineMessageId": 9870, "scanned": 3, "candidates": [9876]}
}}
```

`task:chat:update` добавляет в `operation` поля `chatId` и `messageId` (ID уже известен из проверки привязки).

### 5. Ссылка на сообщение не формируется

Формат `https://<portal>/online/?IM_TASK=chat<CHAT_ID>&IM_MESSAGE=<MESSAGE_ID>` из issue не найден в официальной документации (MCP-поиск 18.11.2026). Генерация недокументированного URL закрепила бы в контракте CLI формат веб-интерфейса, который может меняться. Ответ содержит `chatId`, `dialogId` и `messageId` — клиент собирает ссылку без дополнительного вызова. Если формат будет подтверждён документацией, `messageUrl` добавляется отдельным изменением.

## Risks / Trade-offs

- Два дополнительных чтения до записи и одно-четыре после: приемлемо для команды записи.
- Без scope `im` отправка, работавшая раньше, блокируется. Принято ради единообразия `task:chat:*` и проверяемого результата; диагностика scope подсказывает исправление.
- Окно гонки между `im.dialog.get` и записью безопасно: чужие сообщения отсекаются автором и текстом, свои одинаковые дают `ambiguous`.
