# Design

## Context

См. `proposal.md` для мотивации. В `dev` уже есть четыре бейджа, `src/Bootstrap/CommandCatalog.php` регистрирует 30 прикладных команд. Подробные инструкции находятся в README; отдельных `docs/` пока нет. Требование `worktree-development: Documented setup and safe cleanup` и аудит extensions из `docker-cli-environment` не требуют размещения именно в README, но требуют сохранить документацию в репозитории.

Публичных Releases на момент первоначального планирования нет. Issue #14 определяет три платформы и имена архивов. Перед публикацией плана worktree обновлён до `dev` / `56654f1`: сборочная инфраструктура PR #17 уже принята в `dev`, включая `build/README.md` и native CI-матрицу.

## Goals / Non-Goals

**Goals:** дать короткую навигацию по загрузкам и командам, убрать инструкции разработки с главной страницы, сохранить достоверность ссылок.

**Non-Goals:** менять runtime, создавать новые commands, nightly releases, installers, автоматический обновитель README или сборочную инфраструктуру.

## Decisions

1. **Структура:** название и одно предложение; компактный блок четырёх бейджей; таблица трёх платформ; таблица команд, сгруппированных по namespace, с однострочными описаниями; один пример `b24cli help COMMAND`; одна ссылка на документацию разработки. Длинный quick start и справочник внутренних механизмов убираются. Альтернатива — переставить старые разделы — не достигает запрошенного сокращения.
2. **Загрузки:** при наличии публичного Release с полным набором трёх архивов использовать проверенные `https://github.com/mesilov/bitrix24-cli/releases/latest/download/<asset-name>`; при отсутствии Release показывать явно обозначенные CI-сборки из одной последней успешной native-матрицы, с конкретными ссылками на artifacts каждой платформы и run. Предпочитать актуальную успешную матрицу `dev`; пока новая матрица ещё выполняется, допустима последняя успешная сборка коммита, уже принятого в историю `dev`. При реализации выбран run `38148884407` / `a7024b1`: принадлежность истории `dev` подтверждена, файлы `src`, `bin`, `config` совпадают с базой MR. Предварительную сборку явно отличать от Release. Коротко отметить авторизацию GitHub и ограниченный срок хранения artifacts. Одни ссылки на workflow вместо загрузки и несуществующие Release URLs недостаточны. Сборочная инфраструктура принята в #14; создание публичного Release не входит в этот change.
3. **Каталог команд:** источники истины — фактический `b24cli list --raw`, `CommandCatalog` и встроенные команды Symfony. На текущей базе — 30 прикладных команд плюс `completion`, `help`, `list`; количество не закрепляется навсегда, при реализации учесть новые зарегистрированные команды. Описания сверять с command help, без пересказа параметров и API contracts. Альтернатива — копировать запланированный OpenSpec каталог — может опубликовать ещё не реализованные команды.
4. **Документация разработчика:** перенести нужные рабочие инструкции в `docs/development.md`, исправить относительные ссылки с учётом вложенного пути, удалить устаревшие утверждения и лишнее дублирование. Сохранить setup/check/lint, обоснование дополнительных extensions, подключение через env и безопасный lifecycle worktree. Полное удаление этих инструкций нарушило бы действующие требования документации.

## Risks / Trade-offs

- [Release ещё не опубликован] → честная маркировка предварительных CI-сборок; повторная проверка состояния #14 при реализации.
- [CI artifacts истекут, статическая ссылка устареет] → ссылки на конкретные проверенные artifacts и страницу workflow для поиска новых; переход на стабильные latest Release URLs после первой публикации. Автоматизация обновления вне scope.
- [Документация расходится с новым runtime] → сравнить список с CLI при реализации; не считать успешную упаковку доказательством работы с живым порталом.
- [Перенос текста ломает ссылки] → проверить пути и Markdown anchors в README и `docs/development.md`.

## Migration Plan

Реализация в ветке issue #18 от актуальной `dev`; изменения README и перенос документации отправить на review в PR с базой `dev`. Откат — возврат документационных файлов из родительского commit; сборки и runtime не затронуты. Архивировать change после реализации и проверки, обновив путь в issue.
