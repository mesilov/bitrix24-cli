# Proposal

## Why

Пользователь настраивает входящий вебхук до первого запуска CLI, но в документации нет сводного ответа на вопрос «какие права отметить, чтобы работали все нужные мне команды». В [#178](https://github.com/mesilov/bitrix24-cli/issues/178) пользователь 0.2.0 узнавал о нехватке прав по одной ошибке `permission-denied` за раз и принял диагностическую строку CLI `This operation used an explicitly admitted REST 1.0 route.` за ограничение портала.

С 0.2.0 в `dev` появилась проверка scope по манифесту ([#149](https://github.com/mesilov/bitrix24-cli/issues/149)) и `auth:status`, а [docs/auth-scopes.md](../../../docs/auth-scopes.md) описывает правила проверки. Чего по-прежнему нет:

- полной таблицы «команда → обязательные scope → REST-маршруты». Сведения разбросаны по абзацам, и часть команд упомянута только косвенно;
- короткого ответа в README: какой набор прав отметить для всех сценариев;
- раздела о том, как отличить нехватку scope от отказа в правах на объект, от политики `strict-rest3` и от информационной строки про REST 1.0.

Таблицу, написанную вручную, легко рассинхронизировать с манифестом: после 0.2.0 `task:chat:send` уже начал требовать `im` ([#223](https://github.com/mesilov/bitrix24-cli/issues/223)), хотя в issue он указан как работающий только со scope задач. Поэтому таблица должна строиться из того же манифеста, который применяет CLI.

## What Changes

- В `docs/auth-scopes.md` появляется раздел «Матрица разрешений». Его строит генератор из `ScopeManifest` и `CommandCatalog::ROUTES`: для каждой команды, обращающейся к порталу, — обязательные группы scope, необязательные источники, условия опций и REST-маршруты с версией API. Отдельной строкой перечислены локальные команды, которым права не нужны.
- Генератор работает в режимах записи и проверки (`make scope-matrix` / `make scope-matrix-check`), а unit-тест сверяет раздел документации с выводом генератора. Если изменить манифест или каталог маршрутов и не обновить документацию, падают тесты.
- В README в разделе о подключении появляется короткая таблица по scope: код, название в интерфейсе вебхука, что без него не работает. Под ней — рекомендуемый полный набор (`task`, `user`, `im`, `disk`, `department`, `sonet_group`; необязательный `call`) и ссылка на матрицу.
- В `docs/auth-scopes.md` появляется раздел «Если портал отказывает в доступе»:
  - где на портале меняются права вебхука;
  - как различать `scope-missing` (exit 4), `permission-denied` с `apiErrorCode=insufficient_scope`, `permission-denied` без него (права пользователя-владельца вебхука на объект), `policy-denied` (`--api-policy strict-rest3`) и информационную строку о явно разрешённом маршруте REST 1.0, которая не требует настройки портала;
  - самодиагностика одной командой `b24cli auth:status NAME` вместо последовательного перебора команд.
- `CHANGELOG.md` получает запись со ссылкой на #178.

Вне объёма:
- отдельная команда `b24cli doctor`: её роль уже выполняет `auth:status`;
- изменение текстов ошибок и диагностических строк CLI;
- обновление агентского скилла в [bitrix24-cli-skill](https://github.com/mesilov/bitrix24-cli-skill): это отдельный репозиторий, скилл может ссылаться на новую матрицу;
- шаги создания вебхука и объяснение URL: их покрывает change `explain-webhook-setup` по [#152](https://github.com/mesilov/bitrix24-cli/issues/152). Он должен ссылаться на эту матрицу, а не вести собственную таблицу прав.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `connection-scope-validation`: два новых требования.
  - «Published scope matrix matches the manifest» — документированная матрица строится из манифеста и каталога маршрутов, её актуальность проверяется тестом.
  - «Access denial troubleshooting guide» — документация различает причины отказа и описывает самодиагностику через `auth:status`.

  Поведение проверки scope, состояние и коды ошибок не меняются.

## Impact

- Код: генератор матрицы (класс без ввода-вывода и скрипт `scripts/scope-matrix.php`), цели Makefile. Runtime-поведение CLI не меняется: манифест, маршруты и тексты ошибок остаются прежними.
- Тесты: новый unit-тест сверки матрицы и документации; тест покрытия, что каждая команда с маршрутами есть в матрице, а каждая заметка об условии ссылается на существующую пару команда/scope.
- Документация: `docs/auth-scopes.md`, README, `CHANGELOG.md`; `docs/development.md` — команды генератора рядом с `cli-reference`.
- API: новых REST-методов и scope нет.

Официальные источники (MCP документации Битрикс24, `https://mcp-dev.bitrix24.tech/mcp`, 23.11.2026):
- [Доступные скоупы Битрикс24](https://apidocs.bitrix24.ru/api-reference/scopes/permissions.html): коды и названия `task` «Задачи», `im` «Чат и уведомления», `user` «Пользователи» с вариантами `user_basic`/`user_brief`, `disk` «Диск», `department` «Структура компании», `sonet_group` «Рабочие группы соцсети», `call` «Телефония»; `tasks` — устаревший; вызов вне выданного scope возвращает `insufficient_scope`; для вебхука права выбирают на шаге «Настройка прав».
- [Как выполнить свой первый запрос к API](https://apidocs.bitrix24.ru/first-steps/first-rest-api-call.html): путь *Разработчикам → Готовые сценарии → Другое → Входящий вебхук*, блок *Настройка прав*, запросы выполняются с правами создателя вебхука; `profile` не требует scope.
- `bitrix-method-details` по всем 59 методам манифеста: заявленный scope совпадает с манифестом с учётом уже задокументированных расхождений `task`/`tasks` и `sonet`/`sonet_group`; `im.call.get` в документации отсутствует, в манифесте он описан как `im`. Полный список с URL — в design.

Снимок планирования: `dev` `8013028`.

## GitHub issues

Под «explicitly admitted routes» в issue понята диагностическая строка CLI о политике `task-v3`, а не ограничение портала, — это объясняется в документации.
- Milestone: `0.3.0`; label: `documentation`.
