# Proposal

## Why

На порталах с более чем 10000 задач обход `task:list`/`task:find` по `id ASC` исчерпывает бюджет на старых задачах. Свежая задача оказывается недоступной для проверки дублей даже с фильтром группы.

## What Changes

- Обе команды по умолчанию запрашивают REST3 страницы по `id DESC` и сохраняют порядок обхода в выводе.
- `task:find` принимает такой же повторяемый `--order FIELD:asc|desc`, как `task:list`; явная сортировка списка сохраняется.
- JSON metadata показывает фактический `order`. Для неполного обхода обычный/plain вывод объясняет причину, число просмотренных задач и порядок; исчерпание бюджета предлагает увеличить `--max-scan` и предупреждает, что отсутствие совпадений не доказывает отсутствие дублей.
- Заголовок и группа продолжают фильтроваться локально: документированный REST3 серверный фильтр поддерживает только `id`.

## Capabilities

### New Capabilities

Нет.

### Modified Capabilities

- `cli-experience`: порядок ограниченного обхода, управляемая сортировка поиска и диагностика неполных результатов.

## Impact

`TaskInputMapper`, команды list/find, `TaskListScanner`, `ResultPresenter`, unit fixtures, README и CHANGELOG. Маршрут остаётся `tasks.task.list` REST 3.0; дополнительных API-зависимостей, fallback и серверных фильтров группы/title нет.
