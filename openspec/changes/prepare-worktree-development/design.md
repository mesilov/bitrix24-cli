# Design

## Context

См. `proposal.md` для мотивации и `specs/worktree-development/spec.md` для контракта. В текущем checkout `Makefile` вызывает `docker compose` без явного имени проекта; Compose содержит общий `image: bitrix24-cli-php-cli:dev` и bind mount `.:/var/www/html`. `vendor/` находится в checkout; Dockerfile задаёт Composer cache внутри контейнера. Фиксированных портов, `container_name`, named volumes и дополнительных сервисов сейчас нет. `.gitignore` исключает `vendor/`, `.env`, `.env.local`, но не каталог worktree.

Базовая инфраструктура доступна в `dev` (`88a31a3`). План сверён с файлами этой ветки; worktree реализации создаётся от актуальной `dev`. Незакоммиченные изменения основного checkout не входят в эту задачу.

## Goals / Non-Goals

**Goals:** единая схема адресации Compose для всех Make-команд; проверяемая независимость двух окружений; работа с путями checkout, содержащими пробелы, и одинаковыми basename.

**Non-Goals:** автоматическое создание веток и управление Git; общий изменяемый `vendor/`; автоматическая синхронизация `.env`; запуск прикладных запросов к порталу; добавление сетевых сервисов ради тестирования.

## Decisions

1. **Идентичность по физическому абсолютному пути checkout.** Вычислять валидное Compose-имя с префиксом проекта и устойчивым хешем пути в небольшом переносимом helper, вызываемом из Make. Использовать POSIX-инструменты, доступные на macOS/Linux, и явно проверять необходимую утилиту хеширования. Basename без хеша не различает одинаковые названия; ручное имя требует настройки каждой задачи; имя ветки меняется при переключении и непригодно для адресации уже запущенных ресурсов. Не опираться на то, что `.git` обязательно является каталогом: в linked worktree это файл.
2. **Единая точка вызова Compose.** Все Make-цели используют одно вычисленное имя и явные пути Compose-файла и project directory, относящиеся к выбранному checkout. Это предотвращает расхождение между `build`, `run`, `up` и `down`. Для диагностики выводить имя проекта и путь checkout отдельной командой без содержимого локальной конфигурации. Для прямого вызова Docker Compose README должен показать получение того же имени и аргументов; простой вызов без них не считать поддержанным workflow.
3. **Уникальные теги образов.** Убрать общий фиксированный `image` и использовать имя собираемого образа, которое Compose формирует из project/service. Общие Docker build cache layers допустимы: это не общий изменяемый тег. Вариант с отдельной переменной тега сложнее и создаёт ещё один источник идентичности.
4. **Файлы принадлежат checkout.** Сохранить отдельный bind mount, локальный `vendor/` и передачу UID/GID для каждого окружения. Не вводить общий writable cache или volume. Свежий worktree подготавливается `make docker-init`; локальные секреты при необходимости добавляются пользователем явно, их значения не выводятся и не попадают в Git. `/.worktree/` и действительно создаваемая helper-метаинформация исключаются из Git; worktree за пределами корня также поддерживается.
5. **Очистка адресована текущему проекту.** Использовать существующий `docker-down` с тем же именем проекта. Не применять глобальный Docker prune и удаление других checkout. Документировать остановку окружения до `git worktree remove`; не добавлять принудительное удаление пользовательских файлов.
6. **Приёмка через два checkout.** Проверка создаёт временные worktree из коммита с реализованным окружением, включая пару одинаковых basename, запускает сборку и подготовку параллельно, проверяет Compose labels, image tags и bind mounts. Сентинелы в checkout и `vendor/` проверяют независимость записи; `make cli`, `make check` и запуск оставшегося окружения после остановки первого подтверждают рабочий workflow. Cleanup по trap затрагивает только тестовые проекты и checkout; при ошибке сохраняет понятную диагностику. Нужны Docker и сеть для первоначальной установки зависимостей; live credentials Bitrix24 не требуются.

## CI build correction (2026-10-08)

Проверки Ubuntu/amd64 несколько раз получили HTTP 504 от PECL при скачивании excimer 1.2.6 и yaml 2.3.0. Сохранить Debian Bookworm, PHP 8.4 и весь набор расширений; для двух внешних расширений использовать поддержанную установщиком загрузку из официальных GitHub upstream-репозиториев по полному commit SHA соответствующего релиза:

- excimer 1.2.6: `wikimedia/php-excimer@cc87c1e297cc39398ca786c41a486a3c1f17c8c3`.
- yaml 2.3.0: `php/pecl-file_formats-yaml@c1f0d8ba5ef3884846261bbdb91c2ab0b07db44c`.

Изменяется источник загрузки, а не состав runtime. Проверить наличие и версии расширений в контейнере; не пропускать сборку или тест изоляции при сетевой ошибке. Удалить path filters workflow, чтобы GitHub CI запускался на последнем коммите MR даже после изменения только артефактов OpenSpec. Оставить один pull_request run для feature-веток, push runs для `dev`, чтобы не дублировать тяжёлую проверку. Отчёт о первоначальном CI-сбое сохранить как историю, добавив успешные результаты после исправления.

Источники: [installer source support](https://github.com/mlocati/docker-php-extension-installer/tree/2.4.0#installing-an-extension-from-its-source-code), [excimer 1.2.6](https://github.com/wikimedia/php-excimer/tree/cc87c1e297cc39398ca786c41a486a3c1f17c8c3), [yaml 2.3.0](https://github.com/php/pecl-file_formats-yaml/tree/c1f0d8ba5ef3884846261bbdb91c2ab0b07db44c).

## Risks / Trade-offs

### Integration of accepted Alpine baseline

После первой успешной CI-приёмки в `dev` принят MR #9 (`903dc64`) с актуальной `docker-cli-environment` spec: `php:8.4-cli-alpine3.23`, встроенные PHP-модули плюс `bcmath` и `intl`, без дополнительных excimer/yaml/pcntl/zip и без extension installer. Синхронизировать MR #3 с этой базой и сохранить Dockerfile из `dev`; предыдущая временная фиксация источников excimer/yaml относится к исторической Debian-конфигурации и теперь заменена принятым Alpine-окружением. Это не изменение требований worktree-изоляции.

Проверка runtime в тесте изоляции должна проверять bcmath/intl и Composer platform requirements из текущего lock, а не требовать модули, намеренно удалённые отдельным принятым change. Все четыре линтера должны по-прежнему запускаться через общий wrapper; окончательный HEAD должен пройти CI и быть совместимым с текущей `dev`.

- [Новый путь checkout меняет идентичность проекта] → перед перемещением остановить старое окружение, затем подготовить его в новом пути; документировать это поведение.
- [Дополнительные образы и зависимости занимают диск] → объяснить очистку конкретных тестовых ресурсов; не удалять общие кеши автоматически.
- [Обход Make приводит к другой идентичности] → документировать поддержанный прямой вызов Compose с теми же параметрами.
- [Проверка в свежем worktree не видит незакоммиченные файлы] → испытание проводить на коммите с полной инфраструктурой и реализованным окружением.

## Migration Plan

1. Перед применением изменений остановить окружение текущего checkout старой командой `make docker-down`, чтобы не оставлять ресурсы с прежним именем.
2. После обновления запустить `make docker-init`, при необходимости `make docker-up`; `vendor/` и локальные файлы сохраняются.
3. Для отката остановить окружение новой командой до возврата старой конфигурации. Не удалять пользовательские локальные файлы и зависимости.
