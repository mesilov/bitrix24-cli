# Design

## Context

Зачем нужен change — см. proposal.md, раздел «Why». Требования — в `specs/connection-configuration/spec.md`.

Текущее состояние `dev` на a5f6af1, после #214 и до #178:

- `AuthCommandRunner::login()` сначала выполняет локальные проверки (`assertCanLogin`: существующий NAME без `--replace`, `--replace` для отсутствующего NAME, политика `strict-rest3` без `--skip-check`, конфликт stdin), затем `secret()`. В TTY `secret()` задаёт скрытый `Question('HTTPS incoming webhook: ')` в stderr (`getErrorOutput()`); при `--webhook-stdin` читает stdin; без TTY и без `--webhook-stdin` возвращает usage-error.
- Справка `LoginCommand` подробно описывает проверку при входе, `--replace` и CI, но не происхождение вебхука.
- `docs/auth.md`, раздел «Первый запуск», и README говорят только «Подготовьте входящий вебхук портала с правами для нужных команд».
- `RussianHelpTest` требует русский текст справки и запрещает в нём слова `scope`, `credentials`, `plaintext`, `redirected` и др.
- [PR #232](https://github.com/mesilov/bitrix24-cli/pull/232) по #178 (открыт) добавляет в README подраздел «Права вебхука» с таблицей кодов и названий scope, а в `docs/auth-scopes.md` — генерируемую «Матрицу разрешений» и раздел «Если портал отказывает в доступе».

## Источники Битрикс24

Проверено повторно 2026-11-26 через официальный MCP документации `https://mcp-dev.bitrix24.tech/mcp` (`b24-dev-mcp`, Streamable HTTP, без секретов): `bitrix-search` → `bitrix-article-details`.

- [Как выполнить свой первый запрос к API](https://apidocs.bitrix24.ru/first-steps/first-rest-api-call.html):
  - путь *Разработчикам → Готовые сценарии → Другое → Входящий вебхук*, блок *Настройка прав*, поле *Вебхук для вызова rest api*, кнопка *Создать*, список *Интеграции*;
  - структура URL `https://your-company.bitrix24.ru/rest/1/<код>/метод`;
  - запросы выполняются с правами создателя вебхука в рамках выбранных scope;
  - секретный код нельзя публиковать и сохранять в логах;
  - `INVALID_CREDENTIALS` и *Перегенерировать*;
  - если REST недоступен на тарифе — [Подключить доступ к REST API](https://apidocs.bitrix24.ru/first-steps/access-to-rest-api.html);
  - [доступ к созданию вебхуков](https://apidocs.bitrix24.ru/first-steps/first-rest-api-call.html#webhook-app-access) выдаёт администратор: *Настройки → Настройки Битрикс24 → Безопасность → Интеграции Битрикс24 → Кому разрешить создавать входящие вебхуки*.
- [Как вызывать методы REST API](https://apidocs.bitrix24.ru/api-reference/how-to-call-rest-api/index.html) — вебхук может создать любой пользователь в пределах своих прав.

Особенность MCP: `bitrix-article-details` подбирает статью по названию нечётко. Статья `first-rest-api-call.html` вернулась по подсказке «Входящие и исходящие вебхуки», а точное название «Как выполнить свой первый запрос к API» дало `how-to-call-rest-api/index.html`. Принадлежность проверялась по полю URL ответа.

Граница проверки: интерфейс портала вживую не открывался. Названия пунктов меню взяты из официальной статьи и сверяются при приёмке (задача 3.2). Статью о доступе к REST на тарифе отдельно не читали, используется только ссылка из официальной статьи.

## Goals / Non-Goals

**Goals:**

- Один канонический раздел о создании вебхука в `docs/auth.md`, на который ведут README, справка и подсказка перед вводом.
- Подсказка перед скрытым вводом, которая не меняет stdout и неинтерактивные сценарии.

**Non-Goals:**

- Список прав вебхука и проверка его против манифеста — это #178.
- Изменение проверки при входе, кодов завершения и текстов ошибок `auth:login`.
- Перевод на английский: документация и справка остаются на русском.

## Decisions

1. **Раздел в `docs/auth.md` с якорем `<a id="incoming-webhook"></a>`, сразу перед «Первый запуск».** Справка и подсказка ссылаются на `https://github.com/mesilov/bitrix24-cli/blob/main/docs/auth.md#incoming-webhook`. Кириллический автоякорь GitHub ломается при переименовании заголовка и плохо копируется из терминала. Отдельный `docs/webhook.md` отклонён: руководство по входу уже есть, третий документ о подключении только запутает.

2. **Права — ссылкой на #178, без собственной таблицы.** Шаг «В блоке *Настройка прав* отметьте нужные права» ведёт на README «Права вебхука» (рекомендуемый набор) и на `docs/auth-scopes.md#матрица-разрешений` (точная матрица). Матрица генерируется из `ScopeManifest` и проверяется тестом в #178. Вторая таблица здесь разошлась бы с ней. Тест сверки из прошлой версии change удалён.

3. **Подсказка — только в интерактивном пути `secret()`, в тот же stderr, что и вопрос.** Три строки, без слов, запрещённых `RussianHelpTest`:
   ```
   Вставьте URL входящего вебхука Битрикс24. Ввод скрыт: в адресе есть секретный код.
   Где взять: Разработчикам → Готовые сценарии → Другое → Входящий вебхук, поле «Вебхук для вызова rest api».
   Пошаговая инструкция и права: https://github.com/mesilov/bitrix24-cli/blob/main/docs/auth.md#incoming-webhook
   ```
   Строка вопроса — `URL входящего вебхука: `. Подсказка печатается после проверки TTY и непосредственно перед `QuestionHelper::ask`. Все ранние ошибки из `assertCanLogin` и проверки политики происходят раньше `secret()`, поэтому подсказку не показывают. Многострочный текст внутри самого `Question` отклонён: скрытый ввод в консоли Windows хуже переносит многострочный вопрос.

4. **Справка `auth:login`.** В начало `setHelp` добавляется абзац: что такое вебхук, путь в интерфейсе, что права отмечаются в *Настройка прав* (словом «права», а не «scope»), почему ввод скрыт, ссылка на `#incoming-webhook`. Существующий текст о проверке, `--replace` и CI остаётся ниже без изменений.

5. **Ссылки на официальную документацию — на `apidocs.bitrix24.ru`.** Это русская версия, в ней проверены пути меню. Одна фраза упоминает, что на порталах с английским интерфейсом названия пунктов другие, со ссылкой на `apidocs.bitrix24.com` без пересказа.

6. **Порядок merge относительно #178.** Если PR #232 уже влит, ссылки ведут на «Права вебхука» и «Матрица разрешений». Если нет — на `docs/auth-scopes.md` без якоря и на README «Подключения и конфигурация», а уточнение якорей идёт задачей после merge #232. Перед MR задача 3.3 проверяет, что все ссылки разрешаются.

## Risks / Trade-offs

- [Битрикс24 переименует пункты меню] → путь в справке и подсказке краткий, детали отдаются официальной статье по ссылке; приёмка сверяет пункты на портале.
- [Ссылка на `main` до релиза ведёт на старый документ] → справка и документ попадают в один релиз; якорь при отсутствии раздела открывает начало документа. Риск принимается на время между merge в `dev` и релизом.
- [Смена строки запроса ломает скрипты с `expect`] → документированный путь автоматизации — `--webhook-stdin`; изменение отмечается в CHANGELOG.
- [Конфликт в README с PR #232] → правка README здесь ограничена одной фразой со ссылкой в абзаце перед блоками команд; #232 меняет подраздел ниже. При конфликте сохраняются обе правки.

## Migration Plan

Миграции данных нет. Откат — revert MR: формат конфигурации, credentials и state не меняется.
