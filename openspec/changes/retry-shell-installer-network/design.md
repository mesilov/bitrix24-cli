# Design

## Context

См. `proposal.md`. Установщик использует два вызова curl: определение latest с переходами по redirect и функцию загрузки assets. Существующий Python contract suite проверяет установку через подменённый transport; workflow запускает его на native Linux/macOS. Блоки Bash/zsh в README и `docs/install.md` сейчас содержат независимые команды.

## Goals / Non-Goals

**Goals:** использовать готовую retry-политику curl, сохранить минимальный POSIX installer, проверить реальные сетевые повторы и исполнимые примеры документации.

**Non-Goals:** изменение release selection, API Битрикс24, Windows PowerShell, checksum/архивных контрактов и публикация нового релиза.

## Decisions

### Штатные повторы curl

В оба сетевых вызова добавить `--retry 3 --retry-connrefused`: `--retry-max-time 360` для latest и `--retry-max-time 900` для assets. Штатная задержка — 1, 2, 4 секунды; curl учитывает Retry-After. Сохраняются `--connect-timeout 15`, `--max-time 120` для latest и `--max-time 300` для assets. Бюджет старта повторов втрое больше max-time одной попытки: полный transfer timeout оставляет время для нового запроса. Бюджет запрещает старт новых повторов после его исчерпания, но уже начатая попытка ограничена своим max-time. Верхняя граница передачи с последней попыткой — 480 секунд для latest и 1200 секунд для asset; лимит количества — четыре попытки.

HTTP 404, ошибки сертификатов и package validation не получают повторов. `--retry-all-errors` не используется: он повторял бы постоянные ошибки. Отдельный shell retry-loop добавил бы собственную классификацию ошибок и работу с частично записанными файлами. Native curl уже повторно записывает output-файл при retry.

Официальные источники (проверены через Context7 `/curl/curl`):
- https://github.com/curl/curl/blob/master/docs/cmdline-opts/retry.md
- https://github.com/curl/curl/blob/master/docs/cmdline-opts/retry-connrefused.md
- https://github.com/curl/curl/blob/master/docs/cmdline-opts/retry-max-time.md

### Временный файл для ответа latest

Рабочий каталог и cleanup trap создаются до определения latest; его ответ записывается в обычный `$work/latest`. На Linux curl 8.5 частичный timeout с output=/dev/null не повторяется, а тот же тест с обычным файлом проходит. Curl может усечь output перед новой попыткой. При любой ошибке определения тега cleanup удаляет каталог, как при asset failures. Исходная семантика GET/redirect и проверка конечного публичного tag URL сохраняются.

### Условные шаги в Bash/zsh

Загрузка скрипта выполняется внутри `(set -o pipefail; curl ... | sh)`. Повторы работают внутри install.sh и при предварительном скачивании скрипта в файл. Сам curl в pipeline не повторяет запись тела в stdout: после частичного ответа это могло бы продублировать исполняемый script. Группа связана через `&&` с `. "$HOME/.local/share/b24cli/env"` и `b24cli --version`. `pipefail` действует в subshell и не меняет настройки терминала; source находится снаружи и сохраняет PATH в текущем shell. Одна лишь цепочка `curl | sh && ...` пропустила бы ошибку curl при успешном пустом sh.

В примерах с заранее скачанным скриптом также используются `&&`. Руководство поясняет пределы повторов и явный `--version`, без обещания исправить постоянную недоступность сети.

### Поведенческие проверки

Расширить существующий Python suite. Локальный HTTP сервер задаёт последовательности ответов, а небольшой transport adapter перенаправляет только fixture URL и запускает настоящий системный curl. Для timeout теста max-time и retry-max-time уменьшаются одинаково в 60 раз с сохранением их соотношения; проверяются latest после redirect и частичный archive download. Отказ соединения управляется фактическим curl error 7. Production script не подменяется. Счётчики реальных HTTP попыток подтверждают recovery, предел четырёх запросов и отсутствие retries для 404. Отдельно исполняются фактические fenced blocks README/guide в Bash и zsh, включая download failure при успешном пустом sh и существующей старой установке.

## Risks / Trade-offs

- Повторы увеличивают ожидание → конечные retry count, retry-start budget и per-attempt timeout документированы; конечная ошибка сохраняется.
- Ошибку левой части pipe легко пропустить → тест исполняет скопированный блок целиком, включая `pipefail`.
- Локальная проверка не доказывает устранение исходного внешнего 504 → отдельно фиксируются искусственные сетевые сценарии и native CI; публикация main не входит в эту задачу.

## Migration Plan

Доставка через MR в `dev`; public installer URL продолжает читать `main` до отдельного выпуска. Обновление исходного shell installer не требует пересборки бинарников. Откат — возврат изменений установщика и документации обычным MR.

## Review follow-up

Ревью MR #155 обнаружило, что исходный retry-start budget 120 секунд не позволял повтор после полного max-time 120/300 секунд. Бюджеты увеличены до 360/900 секунд. Regression test сокращает оба таймера пропорционально и обязан пройти после полного таймаута latest и архива. Источник замечания: https://github.com/mesilov/bitrix24-cli/pull/155#discussion_r4285711502
