# Design

## Context

См. proposal.md. База `dev`: `37aa288330e1f70e523dde4f2a9845744cc6aa56`. Раздел «Управление разработкой в GitHub» скилла уже требует milestone и стандартную категоризацию; правка связывает их в одно действие.

## Goals / Non-Goals

Цель — у каждого issue в milestone есть метка типа, выбранная по содержанию issue. Правка не вводит новых labels, не автоматизирует проверку в CI и не меняет уже размеченные issues.

## Decisions

1. **Метка и milestone — одно действие.** Правило добавлено отдельным пунктом сразу после правила о стандартной категоризации. Пример команды `gh issue edit --milestone --add-label` показывает назначение в одной операции.
2. **Выбор по анализу содержания.** Метка выбирается по заголовку и описанию issue, а не по шаблону или автору. Соответствие: `bug` — дефект существующего поведения, `enhancement` — новая возможность или расширение, `documentation` — только документация и инструкции.
3. **Один основной тип.** Вторая метка ставится только когда обе части входят в объём issue. Это сохраняет однозначную группировку отчёта по milestone.
4. **Неясный тип блокирует назначение.** Если тип нельзя определить, мейнтейнер уточняет его и не назначает milestone без метки.
5. **Проверки в workflow.** Шаг 1 «Порядка работы» и пункт 8 «Перед MR» проверяют наличие метки.

## Проверка на портале

Не релевантна: issue меняет инструкции сопровождения и не добавляет и не меняет вызовы REST API.

## Risks / Trade-offs

- Неверный выбор типа → правило требует анализа описания и уточнения при неясности; метку можно исправить через `gh issue edit`.
- Устаревшая локальная копия скилла может затереть разделы `dev` → правка в отдельном worktree от `dev`.
