# Design

## Context

Мотивация и источники приведены в `proposal.md`. Checkout содержит незакоммиченную базовую инфраструктуру, также доступную в удалённой `dev`: PHP `8.4.* || 8.5.*`, b24phpsdk `^3.7`, Symfony Console `^8.0`, Docker-сервис `php-cli` на PHP 8.4. Dev-зависимостей, конфигов этих четырёх инструментов и `.github/workflows/` пока нет. `src/` пока не содержит файлов; точка входа — `bin/console` без расширения `.php`.

Исходные workflows SDK на commit `8ebd4c154d5557db949b0196825f347a3a6c5bf0` запускаются на `push` и `pull_request`, экспортируют UID/GID, логинятся в GHCR, делают `docker compose pull || docker compose build`, устанавливают зависимости и вызывают Make. CLI использует `LOCAL_UID`/`LOCAL_GID`, а собственного опубликованного образа для этих проверок нет. Конфиги SDK содержат пути и исключения, специфичные для SDK. Задача #2 меняет идентичность Compose-проекта; новые цели должны использовать её итоговый механизм вызова Compose.

## Goals / Non-Goals

**Goals:** перенести работающие проверки с общей точкой запуска Make, адаптированными конфигами и раздельными результатами в Actions. Контракт описан в `specs/ci-quality-checks/spec.md`.

**Non-Goals:** тестовые suites SDK, Deptrac, публикация/релизы, настройка branch protection и дополнительная матрица PHP 8.5. Поддержку приложения на PHP 8.5 не менять.

## Decisions

1. **Четыре самостоятельных workflows с исходными именами файлов.** Сохранить назначение исходников, `push`/`pull_request`, Ubuntu runner и отдельные читаемые checks. Единый matrix workflow возможен, но отдельные файлы упрощают сопоставление с четырьмя запрошенными источниками. Ошибки подготовки и линтера не подавлять через `continue-on-error` или успешные заглушки.
2. **Собирать Docker-образ CLI на runner через Make.** Перед сборкой/установкой экспортировать `LOCAL_UID=$(id -u)` и `LOCAL_GID=$(id -g)`; вызывать `make docker-build`, `make composer-install`, затем соответствующую lint-цель. GHCR login и pull SDK-образа не переносить: это создаёт лишнюю зависимость от registry и token permissions. Проверки не требуют секретов портала или публикации образов, включая fork PR. Использовать минимальные разрешения workflow `contents: read`.
3. **Инструменты — прямые dev-зависимости CLI.** Добавить `lendable/composer-license-checker`, `friendsofphp/php-cs-fixer`, `phpstan/phpstan`, `rector/rector`; ориентироваться на версии источника, совместимые с PHP 8.4, и обновить `composer.lock`. Dev-зависимости подключённого SDK не устанавливаются автоматически как инструменты CLI. Установка в CI выполняется из lock с dev-пакетами, без `composer update`.
4. **Конфиги адаптируются к CLI.** License checker использует `.allowed-licenses.php` с исходным allowlist `MIT`, `Apache-2.0`, `BSD-3-Clause`. PHP-CS-Fixer переносит PSR-12; PHPStan — level 5; Rector — правила источника для PHP 8.4 с применимыми исключениями. Не переносить SDK bootstrap, отсутствующие пути и подавления специфичных ошибок SDK. Анализировать `src/` и явно включать `bin/console` (обычный поиск `*.php` его пропустит); существующие PHP-тесты добавлять при появлении. Пустой `src/` учитывать без фиктивных файлов.
5. **Единый Make workflow.** Новые цели используют существующий `RUN`/Compose механизм CLI, в том числе изоляцию из #2, вместо копирования SDK Makefile. PHP-CS-Fixer: `check --verbose --diff`; PHPStan: `analyse` с подходящим memory limit; Rector: `process --dry-run`; license checker: проверка через vendor binary. `lint-all` объединяет только эти четыре проверки; кеши инструментов исключаются из Git. README объясняет подготовку и запуск.

## Risks / Trade-offs

- [Копирование SDK-путей приводит к ошибке либо неполному анализу] → явно включить `bin/console` и проверить диагностику намеренного нарушения в нём; оставить только CLI-пути.
- [Новые dev-пакеты требуют лицензий вне allowlist] → проверить весь установленный набор; не расширять allowlist и не подавлять ошибки автоматически. При несовместимости зафиксировать конкретную зависимость и согласовать изменение политики отдельно.
- [Изменения Make/Compose по #2 конфликтуют с новыми целями] → реализовать от актуальной `dev` и использовать итоговую общую точку запуска Compose.
- [Четыре workflows повторяют сборку и установку] → принять повторение для первого переноса; оптимизацию кеширования выполнять отдельно при подтверждённой необходимости.

## Migration Plan

Реализацию выполнять в отдельном worktree от актуальной `dev`; текущие незакоммиченные изменения не переносить и не перезаписывать. Обновить dev-зависимости и lock, добавить конфиги/Make-цели, затем workflows и документацию. Подтвердить локальные положительные и отрицательные проверки и сохранить ссылки на успешные Actions runs. Откат — revert изменений задачи без удаления пользовательских файлов. Change архивировать только после реализации и проверки соответствия; при архивировании обновить путь в issue.
