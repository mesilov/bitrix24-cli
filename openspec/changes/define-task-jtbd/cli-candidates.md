# Потенциальная CLI-поверхность для новой карточки задач

Статус: кандидаты для проектирования, не реализованные команды и не утверждённый MVP. Дата: 2026-10-09. Связь: [issue #10](https://github.com/mesilov/bitrix24-cli/issues/10), change define-task-jtbd, [согласованные JTBD](../../specs/task-workflows/spec.md), [JSON каталога](cli-candidates.json), [проверка покрытия](jtbd-coverage.md).

Проверен текущий HEAD официального b24restdocs: `b4d3dc81619625c2bf21c28dd0227116f36c8743`. Новый каталог учитывает новую карточку и заменяет предложенный набор 79 имён из исторического исследования как основание для дальнейшего проектирования. Исторический архив сохраняется без изменений.

Всего 55 имён: **42 кандидата** и **13 отложенных расширений** с прежним API. 42 включают 19 task REST3 маршрутов (18 прямых и list с client filtering), 3 IM companion routes, 7 lifecycle gates, 2 локальных REST3 сводки и 11 команд с невыбранным контрактом рабочих данных. Наличие имени не закрывает JTBD.

JSON содержит method_routes с API version и SDK wrapper/core-gap для закреплённого b24phpsdk 3.7.0 (8ebd4c154d5557db949b0196825f347a3a6c5bf0). CRUD/schema/access/chat.send/file.attach имеют task wrappers; v3 list/result/gantt gaps требуют явного Core v3. IM inventory не проверен. Атрибуты scope TaskServiceBuilder и старые примеры docs не заменяют фактическую ApiVersion; совпадение имени метода REST1/3 не разрешает выбрать версию по одному имени.

## Версионная политика

Обсуждения — только task chat: отправка `tasks.task.chat.message.send` через `/rest/api/`, никакого `task.commentitem.*` или legacy result-from-comment. Новая карточка и REST3-only — разные ограничения: официальная миграционная страница оставляет некоторые прежние методы рабочими и прямо направляет чтение/изменение/удаление сообщений в IM.

Для новой карточки основной task CRUD/result/file/schema/access — REST3, scope tasks. Для истории чата — документированный IM route, scope im. Имя API-версии и методы каждого шага должны попадать в meta, не скрываться общим названием команды.

Предложение для конфигурации реализации: политика `task-v3` разрешает документированные IM companion routes; `strict-rest3` запрещает любой non-v3 запрос. Legacy task extensions требуют отдельного явного разрешения. Ни одна политика не переключает маршрут молча после ошибки.

## Карточка, списки и приёмка

Create v3 требует title/creatorId/responsibleId. Fields — camelCase, boolean true/false. Get возвращает связанные объекты через select: `responsible.id`, `creator.id`, `group.id`, `chat.id`; не ожидать responsibleId/groupId там, где они не возвращаются. У list доступны relation IDs, но не связанный объект.

В list REST filter документирован только для id. `--where` — явная локальная фильтрация по selected responsibleId/groupId/status/deadline и другим проверенным полям. `tasks:my` и project views не отправляют эти фильтры в серверный filter и не вызывают legacy list.

Чтобы утверждать полноту выборки, требуется просмотреть все доступные текущему подключению задачи. `--limit` ограничивает выход, `--max-scan` — просмотр; совпадения нельзя искать только в первой странице. V3 page size default50/max1000. Scan cap, transport failure, нехватка разрешений или данных отражаются отдельно. Полнота среди доступных задач не доказывает полноту всего проекта; REST-пагинация не обещает атомарный snapshot.

Status v3 документирован в модели полей и принимается update, но update.status не доказан как эквивалент complete/approve/disapprove с task control, обязательным result и side effects. Семь lifecycle commands — gated-кандидаты, до проверки на портале disabled. Специальные legacy endpoints не маскируются под v3. `tasks:assign` меняет responsibleId, а не обещает процедуру делегирования.

## Чат и результаты

Chat list: получить `chat.id/entityId/entityType` v3 и подтвердить привязку к задаче; IM `DIALOG_ID=chat{{ID}}`. LAST_ID загружает более старые сообщения, FIRST_ID — более новые; CLI before/after взаимоисключающие. IM LIMIT default20/max50, фактический ответ может быть больше из-за непрочитанных; это не стандартная task pagination.

Chat send использует fields.taskId/text. IM update/delete требует проверки принадлежности MESSAGE_ID выбранному task chat и прав автора/сервера. Chat update запрещает пустой текст, поскольку API может трактовать его как удаление. Роли JTBD не дают доступ сверх текущей авторизации.

Result и review decision — разные сущности. Result from message использует fields.messageId. File attach принимает уже загруженные Disk IDs; загрузка локального файла не выполняется неявно. Time show читает elapsedTime, но не заменяет полную историю или запись времени.

## Данные рабочих сценариев: предложения, требующие решения

Для рисков, препятствий и договорённостей нет доказанного стандартного writable v3 поля. Accomplices/auditors/tags/userFields не принимаются add/update v3; нельзя обещать сохранение произвольного UF через `--fields`.

Нужны как минимум следующие данные:

| Область | Необходимые факты |
| --- | --- |
| Контекст запроса | clientRef, sourceRef, requestedOutcome, acceptanceCriteria; при обещании — promisedAt и связанные task IDs |
| Препятствие | blockerId, reason, needs, ownerId, nextStep, raised/resolved decision и источник |
| Изменение | changeId, исходные/новые requirements, scope/deadline/responsible, reason, согласующий, решение и факт применения |
| Передача/обратная связь | recipientRef, evidence refs, transferredAt, client feedback source и отдельное решение о client acceptance |
| Сводка | scope, as-of, evidence IDs, следующий шаг, nextUpdateAt либо unknown, состояние полноты |

Это **кандидатный контракт**, не принятая схема хранения. Варианты для следующего решения: структурированный раздел description, журнал типизированных сообщений task chat или явный входной JSON от оператора/другой системы. У каждого варианта есть ограничения; до выбора provider рабочие команды gated. Произвольный текст не парсится в «согласованную истину» по догадке.

Approval события требует проверки действующего лица/полномочий; цитата или запись оператора не выдаётся за подтверждение клиента. Редактируемый/удаляемый чат не является неизменяемым audit trail. Blocked не вводится как вымышленный нативный status.

Delivery/feedback commands только фиксируют предоставленные факты. Они не отправляют email, не пишут клиенту и не утверждают доставку. Report client audience использует явный набор допустимых полей, не автоматическое раскрытие внутренних обсуждений.

## Общий CLI-контракт кандидатов

- `--profile` выбирает подключение; секреты не входят в прикладные аргументы или вывод. Числовые user IDs обязательны там, где сервер их требует; user lookup — отдельная базовая возможность.
- JSON/stdout, диагностика/stderr, один envelope ok/data/meta или ok/error/meta. Для композиций meta описывает шаги, маршруты, область, scan counts, время чтения, evidence и partial/unknown.
- Неопределённые данные выводятся как unknown, а не как «риска нет». При partial exit 6; 0 успех, 2 ввод, 3 auth/permissions, 4 REST error, 5 transport error — предложения из исследованного контракта.
- ISO8601 с offset, различать TASK_ID/MESSAGE_ID/RESULT_ID/ENTRY_ID. Ввод JSON из файла/stdin проверяется до записи.
- Write имеет явное имя; delete требует `--yes` non-TTY или preview+подтверждение в TTY. Dry-run — локальная проверка и план, не доказательство прав.
- Составные записи не атомарны. Proposal/decision/apply, recorded/delivered/client accepted и native approved не смешиваются; каждый шаг даёт собственный результат.
- После timeout записи неизвестно, применил ли её сервер; не повторять вслепую. Отсутствие compare-and-swap не позволяет обещать защиту от гонок одним preflight read.
- Участник может не иметь доступа к связанной сущности или чату; вывод отражает этот предел, не повышает права и не обращается к shared admin account автоматически.

## За пределами этого предложения

Собственный MCP, TUI, фоновые уведомления/watch, календарь ёмкости команды, автоматическая отправка клиенту, полноценные CRM операции, Scrum/flows/templates, bulk orchestration и импорт сторонних метаданных не добавляются этим документом. Согласованные JTBD не требуют всех 55 команд; расширения и administrative delete не являются принятым MVP.
