## Версионная политика

Обсуждения — только task chat: отправка `tasks.task.chat.message.send` через `/rest/api/`, никакого `task.commentitem.*` или legacy result-from-comment. Новая карточка и REST3-only — разные ограничения: официальная миграционная страница оставляет некоторые прежние методы рабочими и прямо направляет чтение/изменение/удаление сообщений в IM.

Для новой карточки основной task CRUD/result/file/schema/access — REST3, scope tasks. Для истории чата — документированный IM route, scope im. Имя API-версии и методы каждого шага должны попадать в meta, не скрываться общим названием команды.

Предложение для конфигурации реализации: политика `task-v3` разрешает документированные IM companion routes; `strict-rest3` запрещает любой non-v3 запрос. Для task:time:add/list/update/delete согласован явный допуск REST 1.0 task.elapseditem.* в MVP при политике task-v3. Восемь checklist/root/item команд также явно допущены через REST1 task.checklistitem.*; остальные legacy task extensions требуют отдельного решения; strict-rest3 отклоняет time entry и checklist/root/item команды до запроса. Ни одна политика не переключает маршрут молча после ошибки.

## Карточка, списки и приёмка

Create v3 требует title/creatorId/responsibleId. Fields — camelCase, boolean true/false. Get возвращает связанные объекты через select: `responsible.id`, `creator.id`, `group.id`, `chat.id`; не ожидать responsibleId/groupId там, где они не возвращаются. У list доступны relation IDs, но не связанный объект.

В list REST filter документирован только для id. `--where` — явная локальная фильтрация по selected responsibleId/groupId/status/deadline и другим проверенным полям. `task:my` и project views не отправляют эти фильтры в серверный filter и не вызывают legacy list.

Чтобы утверждать полноту выборки, требуется просмотреть все доступные текущему подключению задачи. `--limit` ограничивает выход, `--max-scan` — просмотр; совпадения нельзя искать только в первой странице. V3 page size default50/max1000. Scan cap, transport failure, нехватка разрешений или данных отражаются отдельно. Полнота среди доступных задач не доказывает полноту всего проекта; REST-пагинация не обещает атомарный snapshot.

Status v3 документирован в модели полей и принимается update, но update.status не доказан как эквивалент complete/approve/disapprove с task control, обязательным result и side effects. Семь lifecycle commands — кандидаты после MVP; перед будущим допуском нужна проверка на портале. В MVP смена status через task:update --fields/--fields-file, aliases и неявные шаги запрещена. Специальные legacy endpoints не маскируются под v3. `task:assign` меняет responsibleId, а не обещает процедуру делегирования.

## Чат и результаты

Chat list: получить `chat.id/entityId/entityType` v3 и подтвердить привязку к задаче; IM `DIALOG_ID=chat{{ID}}`. LAST_ID загружает более старые сообщения, FIRST_ID — более новые; CLI before/after взаимоисключающие. IM LIMIT default20/max50, фактический ответ может быть больше из-за непрочитанных; это не стандартная task pagination.

Chat send использует fields.taskId/text. IM update/delete требует проверки принадлежности MESSAGE_ID выбранному task chat и прав автора/сервера. Chat update запрещает пустой текст, поскольку API может трактовать его как удаление. Роли JTBD не дают доступ сверх текущей авторизации.

Result и review decision — разные сущности. Result from message использует fields.messageId. File attach принимает уже загруженные Disk IDs; загрузка локального файла не выполняется неявно. Time show читает elapsedTime, но не заменяет полную историю или запись времени.

## Данные рабочих сценариев: предложения, требующие решения

Для рисков, препятствий и договорённостей нет доказанного стандартного writable v3 поля. Accomplices/auditors/tags/userFields не принимаются add/update v3; нельзя обещать сохранение произвольного UF через `--fields`.

Нужны как минимум следующие данные:

| Область | Необходимые факты |
| --- | --- |
| Контекст запроса | clientRef, sourceRef, requestedOutcome, acceptanceCriteria; при обещании — promisedAt и связанные task IDs |
| Препятствие | blockerId, reason, needs, ownerId, nextStep, raised/resolved decision и источник |
| Изменение | changeId, исходные/новые requirements, scope/deadline/responsible, reason, согласующий, решение и факт применения |
| Передача/обратная связь | recipientRef, evidence refs, transferredAt, client feedback source и отдельное решение о client acceptance |
| Сводка | scope, as-of, evidence IDs, следующий шаг, nextUpdateAt либо unknown, состояние полноты |

Это **кандидатный контракт**, не принятая схема хранения. Варианты для следующего решения: структурированный раздел description, журнал типизированных сообщений task chat или явный входной JSON от оператора/другой системы. У каждого варианта есть ограничения; до выбора provider рабочие команды gated. Произвольный текст не парсится в «согласованную истину» по догадке.

Approval события требует проверки действующего лица/полномочий; цитата или запись оператора не выдаётся за подтверждение клиента. Редактируемый/удаляемый чат не является неизменяемым audit trail. Blocked не вводится как вымышленный нативный status.

Delivery/feedback commands только фиксируют предоставленные факты. Они не отправляют email, не пишут клиенту и не утверждают доставку. Report client audience использует явный набор допустимых полей, не автоматическое раскрытие внутренних обсуждений.

## Общий CLI-контракт кандидатов

Применён референс [Command Line Interface Guidelines](https://github.com/cli-guidelines/cli-guidelines/tree/697d6a29fc8c93d3981a755c0c7683507ad39c3e), источник [content/_index.md](https://github.com/cli-guidelines/cli-guidelines/blob/697d6a29fc8c93d3981a755c0c7683507ad39c3e/content/_index.md), проверен 2026-10-09. Авторы: Aanand Prasad, Ben Firshman, Carl Tashian, Eva Parish; лицензия [CC BY-SA 4.0](https://github.com/cli-guidelines/cli-guidelines/blob/697d6a29fc8c93d3981a755c0c7683507ad39c3e/LICENSE). Рекомендации применены к интерфейсу проекта; полный текст гайда не копируется. Проверяемый контракт: [cli-experience](../../specs/cli-experience/spec.md), rationale и соответствие разделам — [design](design.md#cli-guidelines).

- Корневая пользовательская сущность — `task` в единственном числе. Создание — `task:add`, подзадача — `task:subtask:add`; та же add операция используется для результата/записи времени/чек-листа. Имена и число CLI-команд не обязаны совпадать с REST: method_routes остаются отдельным metadata; пользовательские сводки и составные сценарии могут использовать несколько вызовов.
- Публичная команда `b24cli`, имена `task:<action>` и `task:<resource>:<action>`; обычные изменения через --title/--responsible/--description. Один positional ID, связанные IDs через --message/--entry/--item/--blocker/--change/--to. Namespaces разделяются двоеточиями, как в Symfony Console. previous_proposal_name и initial_proposal_name хранят историю предложений, не работающие aliases; отдельный parser для пробельных групп не проектируется.
- --help/-h, `help COMMAND` и --version/-V доступны offline без auth. `b24cli` выполняет встроенную list; `b24cli list task` показывает namespace task; command help начинается с обычных примеров, документирует defaults, API ограничения и следующий шаг. Неизвестные/неоднозначные команды получают подсказку без автоматического исполнения. Стандартные однозначные сокращения Symfony поддерживаются; примеры и скрипты используют полные имена. Встроенные list/help/completion не входят в 59 исследованных прикладных команд.
- --profile выбирает подключение; секреты не входят в аргументы или вывод. Числовые creator/responsible IDs явно обязательны в create; автоматически выбирать пользователя по названию роли нельзя. Lookup/auth/distribution — отдельные будущие возможности.
- Common options до или после command path: --json, --plain, --quiet/-q, --silent, --verbose/-v/-vv/-vvv, --no-interaction/-n, --ansi/--no-ansi, --profile NAME, --config PATH, --timeout SECONDS. --json и --plain взаимоисключающие; -q подавляет обычный вывод, включая JSON, но сохраняет существенные ошибки; --silent подавляет весь вывод и взаимодействие. Для получения JSON не задавать quiet/silent. --dry-run для writes, --force только для удаления. Нечувствительные flags > explicit config > environment > defaults; auth/storage отдельно. --dry-run без short alias -n, чтобы не столкнуться с Symfony --no-interaction.
- При обычной verbosity TTY показывает короткую карточку/таблицу. Non-TTY сохраняет читаемый вывод без цветов/анимаций, формат скриптов выбирается явно. --plain: одна запись на строку, стабильные TSV columns без header, tab/newline экранируются. --json: один object `{data, meta, error}`, meta.schemaVersion=1, error=null при успехе. Все результаты идут в stdout, пояснения/progress/ошибки — stderr; JSON на ошибке тоже валиден и содержит error.code. В meta отражаются routes, steps, scope, scanned, complete, partial reason и outcomeUnknown.
- 0 success (включая пустую complete выборку), 1 execution error (auth/REST/transport), 2 invalid usage/input, 3 partial result, 4 gated/unavailable/API-policy violation, 130 Ctrl-C. Это новый проектный контракт вместо кодов исторического исследования, не breaking change выпущенного CLI. Unknown не выводится как «риска нет».
- File flags принимают PATH либо `-`; --fields принимает JSON object буквально, --fields-file читает object из файла/stdin. `@JSON` убран. --description/--description-file и --text/--text-file взаимоисключающие; два потребителя stdin запрещены. При file `-` и интерактивном stdin — ошибка с примером pipe, а не ожидание. Dates ISO8601 с offset; JSON, обязательные поля и writable fields валидируются до записи; raw status не обходит lifecycle gate.
- В update обычные field flags комбинируются; advanced --fields/--fields-file не смешивается с ними. В create advanced object допускает дополнительные writable поля при отсутствии дубликатов, обязательные поля проверяются в итоговом payload. --description "" очищает описание, отсутствие флага сохраняет его; empty title запрещён.
- List --id повторяется и отображается на server filter; --select FIELD и --order FIELD:asc|desc повторяются. Удобные user/project/status/due predicates локальные; advanced --where/--where-file — альтернативный режим, не смешиваемый с ними. Поддержанные поля/operators должны быть определены до реализации. Default --limit=50, --all снимает output limit, --max-scan=10000 ограничивает просмотр; --all не снимает scan budget. Явный --limit вместе с --all запрещён. Summary commands используют тот же scan budget. Complete относится к доступным задачам, не ко всему проекту или атомарному snapshot.
- Delete показывает объект и требует подтверждения в TTY либо --force в автоматизации. --no-interaction/не-TTY не подтверждает удаление автоматически. Обычное явное редактирование не требует дополнительного диалога. --force не обходит права, input validation или API gates. Dry-run показывает план и маршруты без writes, разрешает обозначенные preflight reads и не подтверждает server acceptance.
- --no-interaction отключает prompts/pager; ANSI отключается по каждому non-TTY потоку, --no-ansi, NO_COLOR и TERM=dumb; JSON/plain всегда без ANSI. Pager не применяется по умолчанию; отдельное расширение — после базового CLI. Timeout default30 seconds на запрос; Ctrl-C прекращает новые шаги и сообщает подтверждённый/неопределённый результат.
- Составные записи не атомарны: proposal/decision/apply, recorded/delivered/client accepted и native approved различаются; meta показывает каждый шаг. После timeout write нельзя слепо повторять create/send/add. Preflight read не обещает compare-and-swap защиту. Недоступные связанные данные/чат не повышают права и не переключают на shared admin account.

### Прямые пользовательские примеры

Это образцы будущего установленного интерфейса, не подтверждение реализации:

```bash
b24cli task:add --title "Подготовить отчёт" --creator 7 --responsible 42 --description "Собрать данные за октябрь"
b24cli task:update 123 --title "Подготовить отчёт за октябрь"
b24cli task:assign 123 --responsible 84
b24cli task:update 123 --description "Добавить сравнение с сентябрём"
b24cli task:update 123 --title "Отчёт" --responsible 84
b24cli task:update 123 --description-file brief.md
printf '%s\n' '{"title":"Отчёт"}' | b24cli task:update 123 --fields-file - --no-interaction --json
b24cli task:list --responsible 42 --project 7 --all --max-scan 10000 --json
b24cli task:chat:send 123 --text "Нужны данные за сентябрь"
b24cli task:update 123 --title "Отчёт" --dry-run
b24cli task:delete 123 --force --no-interaction
b24cli task:update --help
b24cli help task:update
b24cli list task
```

## За пределами этого предложения

Собственный MCP, TUI, фоновые уведомления/watch, календарь ёмкости команды, автоматическая отправка клиенту, полноценные CRM операции, Scrum/flows/templates, bulk orchestration и импорт сторонних метаданных не добавляются этим документом. Полный каталог не является обещанием состава первого релиза: граница MVP и API-policy-pending описаны выше. Реализация и проверки кандидатов готовятся отдельными changes.

## Чек-листы, пункты и поиск title

Task:checklist:add создаёт корень с PARENT_ID=0; task:checklist:list показывает корни. Task:checklist:item:add требует --checklist; optional --parent должен принадлежать этому корню. Item:list показывает дочерние элементы выбранного чек-листа; update меняет только title. Complete/renew/delete не принимают корневой ID. API task.checklistitem.* представляет дерево плоским списком без пагинации. Все восемь команд включены в MVP через явный REST1 допуск; strict-rest3 не выполняет их. Item:complete/renew не меняют lifecycle status задачи.

Task:find --title TEXT ищет буквальную подстроку без учёта регистра Unicode только в заголовке. Это новая read-only команда MVP: REST3 list + локальная фильтрация. Limit50, max-scan10000, --all, partial и complete имеют общую семантику списков; --all не снимает scan cap. Description/chat не участвуют, wildcard/regex/fuzzy и серверный title filter не обещаются.

```bash
b24cli task:find --title "договор"
b24cli task:find --title "договор" --all --max-scan 20000 --json
b24cli task:checklist:add 123 --title "Подготовка релиза"
b24cli task:checklist:list 123
b24cli task:checklist:item:add 123 --checklist 456 --title "Проверить сборку"
```

### Список результатов task:find и проверка API

Подтверждён API-контракт по [tasks.task.list v3](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-list-rest-v3.html) и [tasks.task.field.list](https://apidocs.bitrix24.ru/api-reference/tasks/tasks-task-field-list.html): server filter документирован для id, пример metadata помечает title как filterable=false. Title возвращается через select; совпадения вычисляются локально. Дополнительно проверен официальный MCP документации. Это не живой ответ портала: подключение в worktree не настроено.

Task:find всегда возвращает список найденных задач с id/title. Human формат — таблица ID/TITLE, --plain — TSV id/title без заголовка, --json — общий envelope с data.items array. Ноль совпадений даёт пустой массив; одно совпадение остаётся массивом из одного объекта. Автоматическое открытие/выбор задачи отсутствует. Пример формы будущего JSON результата, с условными задачами и полным scan:

```json
  "meta": {"schemaVersion": 1, "query": "договор", "match": "title-literal-case-insensitive", "scope": "visible-tasks", "complete": true, "scannedCount": 20, "matchedCount": 2, "returnedCount": 2, "limitApplied": false},
  "error": null
}
```
