# Spec Delta

## Purpose

Позволить пользователю bitrix24-cli сообщить о проблеме без аккаунта GitHub, получить подтверждение и узнать результат обработки связанного issue, сохраняя приватность контактов и данных портала.

## ADDED Requirements

### Requirement: Discoverable feedback entry points
Система SHALL предоставлять команду `b24cli feedback` и ссылку на внешнюю форму в README/help. Команда MUST работать без подключения к порталу, сохранять локальный отчёт и показывать способ его передачи. Браузер SHALL запускаться только при явном `--open`.

#### Scenario: Headless feedback preparation
- **WHEN** пользователь запускает `feedback` без credentials портала в среде без браузера
- **THEN** он получает локальный отчёт, URL формы и инструкции, без portal/network requests и обязательной авторизации

#### Scenario: Browser unavailable
- **WHEN** пользователь явно выбирает `--open`, но браузер недоступен
- **THEN** команда сохраняет доступ к URL и отчёту и сообщает о невозможности открытия

### Requirement: Minimal inspectable diagnostics
Отчёт SHALL включать только разрешённые данные окружения: версию CLI, ОС, PHP и способ установки. Имя команды и тип ошибки SHALL включаться только в безопасной нормализованной форме. Система MUST исключать raw argv, env, webhook URL, токены, REST payload и данные задач; просмотр и редактирование SHALL предшествовать передаче.

#### Scenario: Sensitive runtime context
- **WHEN** подготовка выполняется в окружении с webhook/token и аргументами с данными задачи
- **THEN** отчёт не содержит этих значений, полного окружения, аргументов или ответов портала

#### Scenario: User declines transfer
- **WHEN** пользователь проверяет отчёт и не отправляет форму
- **THEN** данные остаются локально и обращение не создаётся

### Requirement: Submission without a GitHub account
Внешняя форма SHALL принимать описание, ожидаемое/фактическое поведение и шаги воспроизведения без GitHub-login, OAuth, token или регистрации отправителя. Диагностика и email MUST быть необязательными. Перед публикацией выбранного текста SHALL запрашиваться явное согласие с указанием публичности issue.

#### Scenario: No account or contact
- **WHEN** пользователь без GitHub-аккаунта отправляет корректное описание, не прикладывая отчёт и email
- **THEN** обращение принимается и выдаются receipt ID и приватная ссылка на статус

#### Scenario: Missing publication consent
- **WHEN** отправитель не согласился на публичную публикацию текста
- **THEN** публичный GitHub issue не создаётся

### Requirement: Controlled public issue creation
Принятое обращение SHALL проходить validation, ограничения размера/частоты и moderation до публичной публикации. Одобренное обращение SHALL создавать issue от имени сервисной GitHub App в фиксированном репозитории либо связываться с существующим issue. Отправитель MUST NOT управлять credentials или назначением публикации.

#### Scenario: Approved report
- **WHEN** мейнтейнер одобряет безопасный текст обращения
- **THEN** создаётся связанный issue, а статус показывает его URL и результат публикации

#### Scenario: Duplicate or rejected report
- **WHEN** moderation определяет дубликат или отклоняет сообщение
- **THEN** статус объясняет решение; дубликат ссылается на существующее issue, отклонение не создаёт issue

#### Scenario: Oversized or abusive submission
- **WHEN** запрос превышает допустимый размер или лимит частоты
- **THEN** сервер возвращает понятную ошибку и не ставит публикацию в очередь

### Requirement: Reliable receipt and publication state
Система SHALL различать приём обращения и создание issue, сохранять принятую запись до подтверждения и обеспечивать повторяемую обработку без дубликатов. При недоступности GitHub или неопределённом результате API обращение MUST сохранять отслеживаемое состояние; повтор публикации SHALL учитывать уже созданное issue.

#### Scenario: GitHub outage
- **WHEN** сообщение принято, но GitHub недоступен
- **THEN** receipt/status доступны, публикация остаётся ожидающей и не выдаётся за завершённую

#### Scenario: Ambiguous timeout and retry
- **WHEN** GitHub создал issue, но ответ потерян, и обработка повторяется
- **THEN** система восстанавливает связь с созданным issue либо оставляет обращение на проверку без слепого повторного создания

#### Scenario: Repeated submission
- **WHEN** тот же запрос с тем же ключом повторяется после сбоя клиента
- **THEN** возвращается прежний receipt и второе обращение не создаётся

### Requirement: Private contact and status access
Контакт SHALL храниться отдельно от публичного текста и использоваться только по выбору отправителя. Статус и передача уточнений SHALL работать по непредсказуемой приватной ссылке без GitHub-login. Email MUST NOT попадать в issue, diagnostics, URL или логи; удаление контакта SHALL прекращать будущие уведомления.

#### Scenario: Contact omitted
- **WHEN** отправитель не указал email
- **THEN** он может просматривать статус и передавать уточнения по приватной ссылке

#### Scenario: Contact deleted
- **WHEN** отправитель удаляет контакт через приватный канал
- **THEN** будущие email прекращаются, а публичный issue и связь обращения сохраняются без email

#### Scenario: Unrelated visitor
- **WHEN** посетитель запрашивает статус без действующей приватной ссылки
- **THEN** приватные сообщения и контакт ему не раскрываются

### Requirement: Feedback through resolution and release
Статус SHALL отражать triage, запрос уточнений, связанный issue и итог решения. Уточнения SHALL проходить ту же проверку перед публикацией. При выбранном email SHALL доставляться подтверждение и существенный результат. Система MUST различать закрытие issue и выпуск исправления, указывая версию/релиз только при наличии подтверждения.

#### Scenario: Maintainer asks for clarification
- **WHEN** мейнтейнер запрашивает уточнение
- **THEN** отправитель видит запрос без GitHub-login и может ответить через приватный канал

#### Scenario: Issue closed before release
- **WHEN** issue закрыто как исправленное, но релиз ещё не опубликован
- **THEN** статус показывает решение и ожидание релиза, не утверждая доступность исправления пользователю

#### Scenario: Release published
- **WHEN** мейнтейнер указывает опубликованный релиз с исправлением
- **THEN** статус содержит версию и ссылку, а подписанный отправитель получает уведомление

#### Scenario: Replayed event or failed notification
- **WHEN** событие GitHub повторено или доставка уведомления требует повторной попытки
- **THEN** состояние обновляется идемпотентно и уже доставленное уведомление повторно не отправляется

### Requirement: Compatible error hints
Уместная подсказка о `feedback` SHALL выводиться только в человеческой диагностике stderr с учётом quiet/non-TTY. Основные команды MUST сохранять JSON/plain stdout, envelope, коды завершения и отсутствие неявной сетевой отправки после ошибки.

#### Scenario: Machine output error
- **WHEN** основная команда завершается ошибкой с JSON/plain или quiet либо в non-TTY
- **THEN** feedback hint не загрязняет stdout и не меняет контракт или код завершения

#### Scenario: Human interactive error
- **WHEN** основная команда выдаёт подходящую ошибку в человеческом режиме TTY
- **THEN** stderr содержит короткий путь к feedback без секретов и сетевого вызова

### Requirement: Documented operational fallback
README/help и настройки issue templates SHALL описывать внешний канал, обычный GitHub путь и резервный способ передачи локального отчёта. Перед запуском сервиса MUST быть опубликованы владелец triage, правила хранения/удаления сообщений и контактов. Недоступность формы SHALL сохранять возможность описать проблему по резервному каналу.

#### Scenario: Form unavailable
- **WHEN** внешний канал недоступен
- **THEN** пользователь сохраняет отчёт и может воспользоваться документированным резервным каналом без регистрации на GitHub
