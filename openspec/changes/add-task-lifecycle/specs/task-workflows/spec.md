# Spec Delta

## MODIFIED Requirements

### Requirement: EMP-01 — Сотрудник — Выбор следующей работы
CLI SHALL позволять участнику в роли «Сотрудник» увидеть свои актуальные задачи, сроки и согласованные приоритеты.

#### Scenario: EMP-01 — Выбор следующей работы
- **WHEN** сотрудник: планирую рабочий день
- **THEN** участник может увидеть свои актуальные задачи, сроки и согласованные приоритеты
- **AND** достигается рабочая цель: выбрать следующую работу
- **AND** признак успеха: Понятно, что делать сейчас и какие обязательства требуют внимания.

#### Scenario: EMP-01 — Свои задачи по логическому статусу
- **WHEN** сотрудник выбирает работу среди задач, где ответственным указан его собственный ID, и задаёт нужный логический status
- **THEN** CLI позволяет получить свои доступные задачи с этим status и при необходимости ограничить их проектом
- **AND** достигается рабочая цель: выбрать работу или увидеть ожидающую проверки задачу
- **AND** признак успеха: возвращённые responsibleId и status совпадают с условиями; scope/полнота/ограничение вывода видны, ожидание контроля отличается от завершения

### Requirement: PM-02 — Руководитель проекта — Выявление рисков
CLI SHALL позволять участнику в роли «Руководитель проекта» увидеть задачи с риском срыва.

#### Scenario: PM-02 — Выявление рисков
- **WHEN** руководитель проекта: начинается рабочий день или приближается контрольная точка
- **THEN** участник может увидеть задачи с риском срыва
- **AND** достигается рабочая цель: направить внимание туда, где требуется вмешательство
- **AND** признак успеха: Видны просрочки, приближающиеся сроки, препятствия и ожидаемые решения.

#### Scenario: PM-02 — Проект по логическому статусу
- **WHEN** руководитель проверяет ход работ проекта и выбирает конкретное состояние, в том числе ожидание контроля
- **THEN** CLI позволяет получить доступные задачи выбранного groupId с указанным логическим status
- **AND** достигается рабочая цель: увидеть нужный участок работы и определить следующее действие
- **AND** признак успеха: каждый результат соответствует проекту и status; supposedly_completed не смешивается с completed, видимая выборка не объявляется полным проектом без доказательства

#### Scenario: PM-02 — Исполнитель в проекте по логическому статусу
- **WHEN** руководитель уточняет работу конкретного исполнителя в выбранном проекте и состоянии
- **THEN** CLI позволяет одновременно задать responsibleId, groupId и status, объединяя условия через AND
- **AND** достигается рабочая цель: проверить выбранную часть работы исполнителя и направить внимание на неё
- **AND** признак успеха: задачи других исполнителей, проектов или статусов не попадают в результат; недоступные задачи и неполный обход не выдаются за полный список

### Requirement: AM-02 — Аккаунт менеджер — Контроль обещаний клиенту
CLI SHALL позволять участнику в роли «Аккаунт менеджер» отслеживать выполнение связанных задач.

#### Scenario: AM-02 — Контроль обещаний клиенту
- **WHEN** аккаунт менеджер: клиенту обещан результат к определённой дате
- **THEN** участник может отслеживать выполнение связанных задач
- **AND** достигается рабочая цель: заранее заметить угрозу обещанию
- **AND** признак успеха: Можно определить, какие обязательства выполняются, а какие требуют пересогласования.

#### Scenario: AM-02 — Другой исполнитель по логическому статусу
- **WHEN** аккаунт менеджер проверяет обещанный результат, за который отвечает другой сотрудник, и выбирает нужное состояние
- **THEN** CLI позволяет получить доступные подключению задачи указанного responsibleId с заданным status, при необходимости в определённом проекте
- **AND** достигается рабочая цель: оценить ход выполнения перед ответом клиенту
- **AND** признак успеха: исполнитель и фактический логический status соответствуют фильтру; ограничения прав и полноты видны, отсутствие доступа не трактуется как отсутствие работы
