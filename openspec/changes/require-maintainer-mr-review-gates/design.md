# Design

## Context

См. proposal.md. База dev: cf86509593c0608e5456a5331e79d6fd94069720. Локальный основной checkout содержит старую редакцию скилла и новые правила MR; актуальная dev дополнительно содержит JTBD, обязательный MCP, builds/RC и безопасное завершение worktree.

## Goals / Non-Goals

Дополнить действующий workflow понятными условиями готовности MR. Правка не создаёт branch protection, автоматический CI gate или новый формат changelog. Состав runtime-команд и 22 JTBD сохраняется.

## Decisions

1. Считать актуальную dev основой: переносить только согласованные дополнения. Полная замена локальной копией удалит действующие разделы, поэтому отклонена.
2. Расширить существующий раздел changelog на каждый MR и актуальную целевую ветку. Сохранить правила собственного содержательного diff, issue link, Unreleased и повторной проверки после sync/conflicts. Отдельный дублирующий раздел не нужен.
3. Добавить один раздел review между открытием MR и порядком завершения. Пять минут отсчитываются от создания MR; resolved допустим после исправления или согласованного снятия. CI и отсутствие замечаний проверяются отдельно. Workflow открытия MR ссылается на этот раздел.
4. Использовать skip_specs: true по аналогии с документационным change #78. Проверить frontmatter стандартным quick_validate.py, сохранить несвязанные блоки скилла и их ссылки, проверить OpenSpec и changelog. Новые PHP-тесты для текстовых инструкций не нужны.

## Risks / Trade-offs

- Устаревшая локальная копия может затереть новые правила dev → правка в отдельном worktree, сравнение diff с актуальной целевой веткой.
- Зелёный CI не доказывает снятие замечаний → отдельное чтение reviews, threads и комментариев спустя пять минут и непосредственно перед merge.
- Текстовая инструкция не обеспечивает техническую блокировку GitHub → MR описывает правило мейнтейнера, а не автоматическую защиту ветки.
